# real-machine-scheduled-publish-verification — 定时发布真机逐平台验证

## 为什么需要这个任务

2026-10-06 的定时发布全链路验证（`verify-scheduled-publish-completeness`）证明了
**调度机制**正确（单测 + 集成 + 门禁全绿），但**没有产生任何平台真机发布证据**。

必须明确区分两件事：

| 层次 | 已被证明 | 证据 |
|------|---------|------|
| 调度机制 | 是 | scheduler 52 例、IPC 12 例、日历 36 例、resume-guard 8 例、shared-utils 588 例、apps/desktop 13953 例 |
| 平台真机定时发布 | **否** | 无。本任务要补的就是这块 |

## 关键前提：先纠正一个错误认知

注册表 `publish-capabilities.json` 曾把参考产品（4.0 逆向工程）的做法写成本项目的实现，
声称「平台原生定时：抖音 timing、快手 publishTime、B站 dtime」。
实测 `electron/publishers` 对 `prePubTime|dtime|timing[:=]` **零命中** —— 本项目 publisher
根本不消费平台侧定时参数。

**因此本项目的定时语义是统一的**：

```
到点 → 本地 setTimeout → 任务队列 → publisherRouter.createPublisher(platform) → 与立即发布同一条链路
```

这带来一个重要推论：**定时发布在各平台的行为差异，只可能来自各平台 publisher 本身的差异**
（登录态、验证码、风控、内容限制），**不可能来自"该平台是否支持定时"**——
因为定时对平台完全不可见，平台只是到点收到一次普通的立即发布请求。

（已在 `publish-capabilities.test.js` 加结构锁防止 note 再漂移。）

## 逐平台验证矩阵

每个平台需取证三段证据，缺一不算通过：

| # | 证据 | 判据 |
|---|------|------|
| A | 排期创建成功 | UI 提示"已创建 N 个定时任务"；`scheduled-tasks.jsonl` 出现 status=pending 条目 |
| B | 到点确实触发 | 到达设定时刻，条目状态转为 `executed`，任务队列产生入队记录 |
| C | 平台侧真实落地 | 在该平台创作者后台能看到该作品（标题/正文/图片一致） |

### 分批策略（按发布链路形态，不是按平台数量均分）

**第 1 批 — 链路已验证过的平台（先跑通方法论）**

- `toutiao`（头条）：有真机发布取证记录（#2773 ~ #2837 系列），链路成熟，用它验证验证流程本身是否可靠。

**第 2 批 — 主流图文的代表平台**

- `wechat_mp`（公众号）、`zhihu`（知乎）、`weibo`（微博）、`baijiahao`（百家号）

**第 3 批 — 视频类（风险最高，定时 + 视频上传的时序最容易出问题）**

- `douyin`（抖音）、`bilibili`（B站）、`kuaishou`（快手）、`xiaohongshu`（小红书）

**第 4 批 — 海外/长尾**

- `youtube`、`tiktok`、`twitter`、`instagram`、`facebook`、`tencent_video`

## 每平台的执行步骤

1. **前置确认**：该平台账号在本机已登录且会话有效（登录态失效会伪装成"定时失败"）。
2. **建单**：发布页填标题+正文+图片，时间设为**当前时间 + 2 分钟**（留出 RPA 准备余量）。
3. **取证 A**：创建成功提示 + JSONL 条目落盘（记录 id 与 status）。
4. **等待**：到点前后各查一次 JSONL 条目状态；同时观察应用是否仍在运行（**不得中途退出应用**）。
5. **取证 B**：状态应为 `executed`；若为 `failed`，看是否触发了新增的
   `calendarPage.scheduleDispatchFailed` 提示，并记录 reason 与 stage。
6. **取证 C**：登录该平台后台，确认作品真实存在且内容一致。
7. **清理**：测试完成后删除测试作品（避免污染真实账号）。

## 必须额外验证的边界场景

| 场景 | 期望 | 对应修复 |
|------|------|---------|
| 到点时应用已退出 | 下次启动 `restore` 补发（catch-up） | §6.3.7 |
| 排期后取消 | 立即取消成功；已发布的任务提示"无法取消" | 本轮 P0 修复 |
| 批量排期后离开发布页 | 从发布日历取消批次 | 本轮 P1 修复 |
| 排期 30 天以上 | 拒绝并提示"不能超过 30 天" | §6.3.4 |
| 同账号两条定时间隔 < 5 分钟 | 拒绝并提示最小间隔 | §6.3.4 |
| 到点时机器从休眠唤醒 | 立即补发（rearm） | 本轮 P1 修复 |
| 到点时队列不可用 | 立即弹失败提示 | 本轮 P1 修复 |

## 验收标准

- 第 1–2 批平台全部拿到 A+B+C 三段证据，逐平台记录到 `01-docs/` 对应验证报告。
- 任何失败必须区分三类原因：**publisher 缺陷** / **平台侧限制**（如需验证码、频控）/ **登录态问题**，
  不得笼统记为"定时发布失败"。
- 验证过程沉淀为可复用脚本或 checklist，使后续平台能照单执行。

## 前置条件（需人工确认）

- 各平台测试账号与登录态由用户提供/授权；本任务涉及**真实对外发布**，每个平台发布前需用户确认。
- 验证会产生真实公开内容（除非账号为测试专用），须确认发布账号性质。
