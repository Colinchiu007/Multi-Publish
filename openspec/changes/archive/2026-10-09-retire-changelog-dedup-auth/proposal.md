## 实际落地对账（2026-10-09 补写，以本节为准）

**本 change 的 3b 设计（"两侧都无授权文件时按清理前后形状放行"）从未实施，也无需实施。** 实际发生的是：
PR #3151（merge `a3565726`）落地了**另一套更小的退休判据** —— `evaluateAuthorization` 里当
`applies_to_base` 是本次 base 的**祖先**时，视为"那次清理的成果已在 main 上、授权已消费"，
不再报「坐标系不等」fatal，而是继续由 `collect` 层核形状四条与额度数字（`check-changelog-growth.js:340-372`）。
回归锁为 `scripts/check-changelog-growth-retire.test.js`（5 条，含"不是祖先⇒维持 fatal"
与"authBaseText 非 null⇒维持防白蹭 fatal"两条负控）。

**本 change 原前提里有两处推断被当场实测否证，留在下文作历史快照，不得再当作现状引用**：

1. 「清理提交一旦合入 main，所有分叉早于清理的 PR 都卡死」——不成立。实测 #2992（2026-10-06 开，早于清理）
   当前 **8 pass / 11 skipping / 0 fail**：默认判据卡的是**标题丢失**，而清理对每个标题都保留了一份，
   多重集包含关系成立 ⇒ 那类 PR 根本不进授权通路。触发 #3076 现场的是它自己 re-sync 解冲突造成的形状变化，不是"分叉早"。
2. 「授权机制从落库那刻起就锁死了 main」——措辞过强。真实后果是**语义残留**：一次性的授权文件常驻在 main 上，
   而它声明的额度（`expected_entries_after=349`）与今天的台账规模（**369** 条）已不可重合，
   即它既不可能再授予任何事，又让"一次性"这件事失去现场证据。

**因此本 change 的实际范围收缩为一件清理**（用户 2026-10-09 选定方案 A）：删除
`scripts/changelog-dedup-authorization.json`，并加一条**生命周期锁**防止它再次变成常驻文件；
门禁判据与授权通路本体一字不动（未来确需一次性授权时，由 `scripts/changelog-dedup-regen.js` 在**同一个清理 PR**里现生成）。


`scripts/changelog-dedup-authorization.json`（PR #3059 → `88669579` 落库）是
`dedup-changelog-history` 那次清理的一次性书面授权。清理已成功执行并合入 main：
canonical 口径下 1,184 条 / 343 种标题 / 冗余 841 份 → 清理后每个标题恰剩 1 份，
`CHANGELOG.md` 从 65,890 行 / 4.6MB 降到 18,155 行 / 1.27MB，标题种类 1,434 → 1,441
（多的 7 种是后续正常新增），**没有任何标题消失**。

但这个授权机制存在一个**设计缺口**，从落库那一刻起就锁死了 main：

门禁 `check-changelog-growth.js` 的授权通路要求 head **相对 base 新增**该文件
（`evaluateAuthorization`：`authBaseText !== null` 即 fatal「授权文件不是本次新增」）。
而授权文件已经合入 main —— 于是对**任何后续 PR**：

1. 授权通路永远判不成立（文件在 base 里已存在 ⇒ fatal）；
2. 但 head 与 base 的 CHANGELOG 都已是"清理后"的形状，默认判据（标题多重集包含）
   本不该红 —— 真正的红来自 `expected_titles_reduced=269` 那条**授权额度判据**：
   门禁把「base（清理前坐标）有 269 个标题带多份副本、head 只剩 1 份」解读为
   "269 种条目缺失"。

实测复现（PR #3076，base `f210f191`，head `e94f1c18`，该 PR 未触碰 CHANGELOG）：

```
[changelog-growth] FAIL(授权)：授权的 applies_to_base=23822b73fecc 与本次 base
坐标系 f210f191d575 不等 —— 坐标系错位时不得退化成"没有授权"再按普通红混过去
且按默认判据仍报 269 种条目缺失（坐标系 f210f191d5757b38eeec17f549d61857fabe3036）
```

也就是说：**授权完成了一次性清理之后，没有退出通道**。它留在 main 上，让每一个
后续 PR 都撞上「坐标系错位」的 fatal（授权通路永不成立），再退回默认判据、又被
「base 与 head 隔着那次清理」这个既成事实卡住。这不是某个 PR 的错——`#3059`
的清理与授权都是对的，缺的是「清理完成、授权消费完毕之后如何正式退役」这一步。

**不修的代价**：此后所有触碰 CHANGELOG 判据的 PR 全部红在同一个 fatal 上，
且按门禁自己的口径「不得退化成没有授权再按普通红混过去」，无法绕过——只能
把 841 份副本插回去（与 `#3059` 的目的直接相反），或每开一个 PR 就重写一次授权
（门禁明文禁止「被后续 PR 白蹭」）。

## What Changes

- **删除** `scripts/changelog-dedup-authorization.json`（一次性授权，其额度已在
  `88669579` 消费完毕；文件留在 main 上只会让每个后续 PR 撞 fatal）。
- **修改** `scripts/check-changelog-growth.js` 的授权退役条款：当**授权文件在
  base 与 head 中均已不存在**、且 head 的 CHANGELOG 已是「每个标题恰剩 1 份」
  的清理后形状（head 不同标题集合 ⊇ base 不同标题集合，即默认判据的标题包含
  检查通过）时，跳过授权额度判据，按清理后坐标正常放行。
  **默认判据一字不改**：标题多重集包含（base 的每个标题在 head 至少剩 1 份）
  仍然必须通过——本 change 只退役「已消费的授权」，不放宽任何质量要求。
- **删除** `scripts/check-changelog-growth.test.js` 中依赖授权文件存在性的
  用例，**新增**退役条款的回归用例（见 specs）。
- 同步 `openspec/changes/dedup-changelog-history/` 的收尾说明：一次性授权
  已消费并退役，后续不再需要。

## 不做什么

- **不**把 269 个标题的历史副本插回 CHANGELOG——那是把 `#3059` 刚清理掉的
  841 份冗余重新引入，方向相反。
- **不**放宽「标题多重集包含」这条默认判据——base 的每个标题在 head 至少剩
  1 份，这条永远有效。
- **不**触碰 `scripts/changelog-entries.js`（条目模型单一实现）。
- **不**重写 CHANGELOG 台账本身（本 change 只改门禁判据与授权文件的去留）。

## 风险与对策

- **风险**：退役条款可能被滥用（先删条目再以「清理后形状」蒙混）。
  **对策**：条款只跳过**授权额度判据**，「base 每个标题在 head 至少剩 1 份 +
  head 独有标题不得复制多份」这两条默认判据原样保留且先于退役条款执行；
  且退役条款要求「base 与 head 均无授权文件」，授权文件重新出现即回到原通路。
- **风险**：改门禁判据违反「默认判据一字不改」的原始承诺。
  **对策**：原承诺的对象是**默认判据**（防止借授权降低质量标准）；本 change
  退役的是**已经消费完的例外通路**，默认判据一行不动，并有逐字对照测试钉住。
