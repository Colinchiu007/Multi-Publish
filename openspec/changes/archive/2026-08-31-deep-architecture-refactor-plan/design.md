## Context

见 [proposal.md](./proposal.md) 的动机。本 change 是对固定代码基线的架构取证与重构规划，不是一次“大爆炸”重写。分析对象跨 Electron renderer/preload/main、pnpm workspace、Python/Node 服务、运营后台、数据库、云部署和 CI；因此必须把源码证据、历史意图、静态度量、运行边界和外部模型意见分开记录，避免把“可能的设计”写成“已验证事实”。

约束：共享主工作区含其他会话的未提交文档；本任务只在独立 worktree 工作。当前 change 跳过 capability delta，因为本次不改变产品行为。报告中的每个实施波次均需在用户批准后另建 change，并独立完成测试、打包、真实 UI/服务或远端 CI 验证。

## Goals / Non-Goals

**Goals:**

- 建立可追溯到 `file:line`、符号、配置或命令输出的现状架构地图。
- 区分逻辑模块边界、进程边界、数据所有权、信任边界和部署边界。
- 用体量、依赖、复杂文件、重复实现和测试映射识别优先债务，而不是凭主观印象排序。
- 给出增量式目标架构与 6-18 个月迁移波次；每波均可独立交付、回滚和度量收益。
- 把架构建议转成具体的 ADR/OpenSpec 拆分清单、测试金字塔和质量门禁。

**Non-Goals:**

- 不实施任何建议，不新增基础设施，不修改运行行为。
- 不要求一次性统一所有语言、框架或存储；保留有明确边界价值的多语言和多进程设计。
- 不把代码行数或圈复杂度单独当作重写理由。
- 不以本次静态审计证明真实第三方供应商、生产容量、跨设备同步或安装包运行。

## Decisions

### 1. 固定远端基线，隔离并发状态

以 `origin/main@2e1b84fcf42245842ae09554a054a8d5f4b66b07` 为唯一代码基线，在 `codex/deep-architecture-refactor-plan` linked worktree 中产出报告。选择固定基线而不是扫描共享根，是因为共享根落后远端且含其他任务脏改动；混用会让行号、模块状态和结论不可复现。

备选：直接分析共享根。拒绝，原因是会混入未提交状态，且无法安全提交报告。

### 2. 采用“代码优先、文档校准、历史溯源”三层证据

源码和当前配置用于回答“现在是什么”；架构/PRD/OpenSpec 用于回答“原本想是什么”；Git 历史用于解释“为什么演变成这样”。结论至少绑定一层当前代码证据，历史文档和 memory 只能作为线索或约束。

备选：以最新 PRD 为真相源。拒绝，原因是该仓库文档体量大、版本多，规划和实现可能不同步。

### 3. 按独立关注面并行探索，由主线程合并架构模型

将桌面端、业务包/发布引擎、媒体/AI 管线、服务端/部署、测试/工程治理拆成独立只读探索。子代理只返回 `file:line`、符号、关键原文和风险；主线程负责阅读最终要引用的关键代码、处理矛盾并做取舍。

备选：单线程逐目录通读。拒绝，原因是会把大量外围搜索结果带入主上下文，且难以获得独立核验。

### 4. 双模型分两轮使用

第一轮以 analyzer/architect 角色独立诊断现状；第二轮以 reviewer 角色审查最终方案。opencode 侧重点为前端/开发体验/模块边界，Claude 侧重点为架构、安全、迁移和失败模式。两者同意不自动等于事实，所有高优先级结论仍需代码证据。

备选：只在末尾做一次泛化审查。拒绝，原因是无法在方案形成前暴露盲区，也不满足 CCG 双模型规则。

### 5. 目标架构使用渐进式绞杀迁移

优先建立边界、契约、依赖方向和观测能力，再移动实现；结构重构与行为变更分离。每个波次必须有兼容适配层、双写/影子或合同测试（按场景选择）、退出条件与删除旧路径的时间点。

备选：按目录重写桌面端或拆成大量微服务。拒绝，原因是缺乏收益基线、爆炸半径过大，并会消耗不必要的基础设施成本。

### 6. 报告同时给出优先级与否决条件

每项建议按用户影响、风险、耦合收益、实施成本和可验证性评分，并明确“何时不应实施”。这样可防止重构路线图变成无限技术债清单。

备选：仅列 P0/P1/P2。拒绝，原因是无法解释排序，也无法在业务优先级变化时重算。

## Risks / Trade-offs

- [静态分析看不到真实运行频率与生产瓶颈] → 将性能建议标为假设，要求后续先补 telemetry/benchmark 再改架构。
- [仓库在调研期间继续变化] → 固定 commit，报告记录生成时间与基线；实施前重新做 delta audit。
- [外部模型输出可能臆造或遗漏] → 保留原始输出，所有 Critical/高优先级发现需回查源码；分歧单列。
- [报告过大导致不可执行] → 以迁移波次、入口条件和 Definition of Done 组织，每波拆成独立 change，不创建一个全库实施 PR。
- [量化指标诱导错误优化] → 指标只用于定位热点，最终优先级必须结合运行责任、变更频率、故障历史和用户影响。
- [文档变更与并发任务冲突] → 新增独立文件，stage 命名路径；不修改共享 PRD/CHANGELOG 的现有脏文件。

## Migration Plan

本 change 自身无运行迁移。交付步骤为：基线审计 → 并行代码取证 → 静态度量 → 双模型分析 → 草拟报告 → 双模型 reviewer 审查 → 修订与验证 → 归档规划任务。后续实施必须按报告波次逐一创建 OpenSpec change，不允许直接把本 change 转成全库实现。

回滚：删除本分支/报告和 planning artifacts 即可，不影响产品运行。若报告合并后发现基线或证据错误，以新的勘误提交修正文档，不重写 Git 历史。

## Open Questions

- 真实生产故障分布、模块变更频率和用户路径耗时目前没有统一数据源；报告会把它们列为实施前测量项，而不是假定值。
- 外部 Python sidecar 在不同部署环境中的实际启用比例需要运行证据；本次只确认代码与配置支持的边界。
