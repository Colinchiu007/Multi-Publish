# 改写引擎开源项目调研与技术复用分析报告

> 调研日期：2026-09-08 | 版本：v1.0

## 一、调研概述

对 8 个类别的开源项目进行系统性调研，覆盖去 AI 味、文案生成、Prompt 工程、敏感词检测、文本去重、LLM 记忆系统、反馈学习等方向。重点分析其技术架构、核心算法、可复用代码与思路。

**调研来源：** GitHub 实时搜索 + 用户本地 LLM-Wiki-V2 源码精读 + 已知开源项目知识库分析。

## 二、项目详析（A-D 类）

### 2.1 blader/humanizer（去 AI 味黄金参考）★45,231

**技术栈：** Python + Markdown（Agent Skill）

**核心机制：**
- 基于维基百科《Signs of AI writing》整理出 33 个可检测、可修复的 AI 模式
- 多阶段改写流程：标记每个 tell（最强优先）→ 草稿改写（不把原结构当固定）→ 对照模式和原主张校验 → 定稿
- 声音匹配：给 2-3 段个人写作样本，模仿节奏/用词/标点/怪癖
- 事实保真：姓名/数字/日期/引用/引文必须来自原文，缺细节就问而不是编

**可复用点（极高）：**
1. 33 模式清单可直接作为 AI 味检测的基线
2. 多阶段改写流程（标记→改写→校验）替换当前单 pass 后处理
3. 声音匹配机制——比当前口语化映射更精细
4. 事实保真约束——改写引擎必须内建的底线

**对比当前引擎：** 当前 `ai-taste-remover.js` 仅 40 条短语映射 + 7 个开头模式 + 句式随机化，属于「事后清理」模式，缺少「标记→改写→校验」的多阶段流程和声音匹配能力。

### 2.2 op7418/Humanizer-zh（中文去味）★16,907

**技术栈：** Markdown（Claude Code Skill）

**核心机制：** humanizer 的官方中文汉化版，继承 33 模式，针对中文语境本地化

**可复用点（极高）：**
1. 中文 AI 味模式清单——这是最贴近我们场景的去味实现
2. 中文特有的 AI 味特征（如"在当今社会""值得注意的是""综上所述"等——我们当前已覆盖部分，但清单不完整）

**对比当前引擎：** 当前 `AI_PHRASE_MAP` 含 20 条中文映射，远少于 humanizer 的 33 模式（中文版可能更多），且缺少结构层模式的检测。

### 2.3 Nanako0129/sepia（科学化去味）★2,447

**技术栈：** Python + Markdown

**核心机制：**
- 基于 StoryScope 研究（61,608 篇故事，叙事结构特征单独即可 93.2% macro-F1 检测 AI 文本）
- 文体分层：小说修叙事架构，专业文档各配规则
- 四操作分离：write / review（仅诊断）/ refactor（最小编辑）/ recreate（全重写）
- 三层 pass：叙事架构 → 句式节奏 → 用词
- 中文有专门校准（references/languages/zh.md，基于 HC3 语料）
- 关键发现：节奏是唯一跨研究一致的信号——句长分布（人类文本段内变化更大），而非平均句长

**可复用点（极高）：**
1. 文体分层去味——当前引擎对所有内容一刀切，不区分文体
2. 四操作分离——当前只有 process（full rewrite），缺少 review（仅诊断）和 refactor（最小编辑）
3. 句长分布检测——当前只检查平均句长 > 60 或 < 8，但研究显示分布（variance）才是关键，均值无区分力
4. 中文节奏校准——基于 HC3 语料的中文节奏特征

### 2.4 epoko77-ai/im-not-ai（模式分级）★5,325

**技术栈：** Python + Markdown

**核心机制：**
- 10 大类别 × 70 子模式，按严重度 S1/S2/S3 分类
- Span 级检测后精确润色（非整篇重写）
- 检测翻译腔、过度英文引用、机械并列、AI 习语、被动滥用、句首连接词滥用、emoji/bullet 滥用

**可复用点（高）：**
1. 严重度分级（S1/S2/S3）——让去味可解释、可审计
2. Span 级定位——比整篇重写更精准，减少误伤
3. 70 子模式清单——可抽取中文部分作为模式库增强

### 2.5 mikiarlo3/ai-copywriter（生成即规避）★1,042

**技术栈：** Python + Markdown（构建在 humanizer 之上）

**核心机制：**
- 生成时主动规避 AI 模式（防患于未然），而非事后改写
- 情感先行：从对方当下的感受出发，用最简单的词解释概念
- 写前先答两个问题：对方此刻是什么感受？决定语气、长度、开头顺序

**可复用点（高）：**
1. 「生成即去味」双向设计——当前引擎是「生成→后处理」，可增加「生成前约束」
2. 情感先行定位——弥补当前引擎缺失的产品语境层

### 2.6 lguz/humanize-writing-skill（结构优先）★44

**技术栈：** Markdown

**核心机制：**
- 3-pass 系统：Pass 1 杀 AI 词汇（36+ 禁用词）→ Pass 2 破 AI 结构（并列否定、三连排比、em dash 滥用、设问、镜像结构）→ Pass 3 加人类质感（变化句长、加缩略、留未解决想法、让作者观点可见）
- 14 点质量清单
- 关键洞察：结构 tell > 词汇 tell

**可复用点（中）：**
1. 「结构优先」的改写顺序——当前引擎先换词再调句式，但结构模式比词汇更标志性
2. 14 点质量清单——可直接作为改写验收标准

### 2.7 Colinchiu007/LLM-Wiki-V2（用户记忆层）★本地

**技术栈：** Python + SQLite + Shell + Markdown

**核心机制（源码已精读）：**
- **混合搜索**（`lib/search.py`）：jieba 分词 + SQLite FTS5 BM25 + 图谱遍历 + RRF 融合（score = Σ 1/(60+rank)）
- **置信度**（`lib/confidence.py`）：Ebbinghaus 遗忘曲线，confidence = (0.5 + min(sources,3)×0.1 + authority×0.2 + min(access_count,10)×0.02) × 0.5^(days/30)
- **知识图谱**（`lib/entities.py`）：8 种关系类型（uses/depends_on/causes/contradicts/supersedes/related_to/part_of/implemented_by），wikilink 解析，DFS 图遍历
- **质量评分**（`lib/quality.py`）：结构 0.3 / 引用 0.4 / 可读性 0.3 加权
- **矛盾检测**（`lib/contradiction.py`）：字符级 bigram Jaccard 相似度 + 否定词扫描
- **隐私过滤**（`lib/privacy_filter.py`）：API Key/密码/手机号/身份证/银行卡/JWT 正则
- **生命周期管理**：active→stale（90 天）→deprecated（180 天）→archived

**可复用点（极高）：**
1. 置信度遗忘曲线——当前 knowledge-base.js 无时间衰减，所有历史同等权重
2. RRF 混合搜索——当前 knowledge-base.js 无搜索能力，仅靠频率排序
3. 知识图谱遍历——当前无实体关系，无法表达「品牌 A 使用风格 B」「平台 C 禁止模式 D」
4. 矛盾检测——当前无，可能导致"用户喜欢幽默风格，但品牌要求正式"的冲突
5. 质量评分——当前无，无法区分"被采纳 10 次的高质量样本"和"仅生成过 1 次的低质量样本"
6. 隐私过滤——当前无，改写结果可能泄露用户隐私
7. 生命周期管理——当前无，知识库无限膨胀

### 2.8 Karpathy LLM Wiki gist（方法论源头）

**核心洞察：** RAG 每次查询从原始文档重新推导，没有积累；LLM Wiki 是增量构建并持续维护的持久 wiki。这是 LLM-Wiki-V2 的方法论地基，也是我们引擎「风格/知识记忆」的设计哲学。

### 2.9 coreyhaines31/marketingskills（营销框架）★48,529

**技术栈：** JavaScript + Markdown（Agent Skill 集合）

**核心机制：** 分层 skill 依赖——「产品营销」是地基，所有其他 skill 先读它，理解产品/受众/定位后才动手。

**可复用点（中）：** 「定位先行」思路——改写前先理解产品/受众/定位，当前引擎缺少此层。

### 2.10 rayguo01/viral-x（爆款流程）★45

**技术栈：** Node.js + PostgreSQL + Claude CLI

**核心机制：** 热点选择 → 内容生成 → 爆款优化 → 生成配图 → 发布。实时热点追踪（X + 国内热点，每小时更新）。写作风格模仿（分析大 V 推文风格一键模仿）。

**可复用点（中）：** 热点追踪 + 风格模仿 + 评分优化闭环。用 Claude CLI 而非 API——省钱做法。

## 三、类别 E-H 技术补充

### 3.1 Prompt 工程框架

| 项目 | 核心机制 | 可复用点 | 代价 |
|------|---------|---------|------|
| DSPy (~25k stars) | 声明式编程 + 自动 few-shot 选择 + 多步推理 | 改写拆成「分析→起草→自检→润色」链 | 中 |
| promptfoo (~6k stars) | 评测矩阵 + A/B 测试 + 回归护栏 | 改写质量回归测试，防 prompt 迭代退化 | 低 |
| Guidance/Outlines/Instructor (10-20k stars) | 正则/JSON Schema 约束解码 | 强制结构化输出 {rewritten, changes, risk_level} | 低 |

### 3.2 敏感词检测

| 项目 | 核心机制 | 可复用点 | 代价 |
|------|---------|---------|------|
| sensitive-words (houbb, ~3k stars) | DFA 自动机 O(n) 匹配 | DFA 匹配器 Node 移植 + 词库分层 | 低 |
| 腾讯云内容安全 | 预训练分类模型 | 本地 DFA + 云端深审 两级过滤 | 低 |

**关键发现：** 当前 `sensitive-filter.js` 仅 2 个示例词，无运营中心同步，无变体对抗（谐音/拆分/拼音）。需要引入 DFA 引擎 + 词库分层 + 变体归一化。

### 3.3 文本去重/改写检测

| 项目 | 核心机制 | 可复用点 | 代价 |
|------|---------|---------|------|
| SimHash | 64 位指纹 + 海明距离 < 3 判重 | 改写充分度检测——改写结果与源文比对，距离过近提示「改写不充分」 | 低 |
| SBERT/text2vec | 句子嵌入 + 余弦相似度 | 改写质量评估：原文 vs 改写文语义相似度 | 中 |

**关键发现：** 当前引擎不评估改写质量——没有「改得够不够」「有没有偏离原意」的量化指标。

### 3.4 LLM 自我进化/反馈学习

| 项目 | 核心机制 | 可复用点 | 代价 |
|------|---------|---------|------|
| TRL (HuggingFace, ~10k stars) | DPO/PPO 偏好学习 | 用户采纳/拒绝沉淀为偏好对，定期 DPO 微调 | 高 |
| LangSmith/Braintrust | LLM 应用可观测性 | 反馈数据管道——点赞/点踩/编辑 → 结构化数据集 | 低-中 |

**关键发现：** 当前 knowledge-base.js 的 `recordFeedback` 在桌面端实际未被调用（前端无反馈上报链路），且 `strategy-matcher.js` 的历史评分维度恒为 30% 基础分。反馈闭环完全断裂。

## 五、推荐复用路线图

### 短期（低代价，直接收益）

1. **去 AI 味增强**
   - 吸收 humanizer 33 模式 + Humanizer-zh 中文模式，扩展到 AI_PHRASE_MAP
   - 引入 sepia 的分层去味（叙事架构→句式节奏→用词）
   - 引入 lguz 的「结构优先」改写顺序
   - 修正 detectAITasteLevel 的句长检测逻辑（分布 > 均值）

2. **敏感词引擎升级**
   - 移植 DFA 匹配器到 Node（~200 行）
   - 词库分层（政治/色情/暴力/广告）
   - 变体归一化（谐音/拆分/拼音）

3. **改写质量评估**
   - SimHash 改写充分度检测（是/否充分改写）
   - promptfoo 式评测矩阵（回归护栏）

### 中期（中代价，提升质量）

4. **知识库升级**
   - 吸收 LLM-Wiki-V2 的遗忘曲线、RRF 搜索、知识图谱
   - 接入桌面端 SQLite 持久化
   - 修复反馈闭环（前端上报→知识库更新→策略匹配提权）

5. **Prompt 编排优化**
   - DSPy 风格多步推理链（分析→起草→自检→润色）
   - 结构化输出契约（rewritten + changes + risk_level）
   - 生成前 AI 规避约束（ai-copywriter 思路）

6. **文体分层**
   - sepia 四操作分离（write/review/refactor/recreate）
   - 小说 vs 营销文案 vs 专业文档 各配规则

### 长期（高代价，形成壁垒）

7. **反馈闭环 + 数据飞轮**
   - 用户采纳/编辑沉淀为偏好对
   - DPO 微调（如条件允许）
   - 知识库从「使用频率统计」升级为「质量评分 + 置信度衰减」

8. **爆款能力增强**
   - 热点信号输入 + 平台适配策略 + 风格模仿
