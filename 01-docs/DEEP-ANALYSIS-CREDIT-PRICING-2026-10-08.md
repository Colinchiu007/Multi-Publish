## 〇、执行摘要

**结论先行，六句话：**

1. **你原方案的四点骨架成立**，但其中两条隐含假设会让运营方亏本——「两档都能用全部内置模型」和「积分换算需跟成本挂钩」。后者你已自己点出，前者需要靠 `tier_access` 落地。

2. **积分体系目前是「有字段、无引擎」**。`officialCreditMonthly`（500 / 3000）已定义并下发到 entitlement，但**全仓无 `consumeFeature('official_credit')`**，`official_credit` 甚至不在 `features` 数组里。当前唯一真实的扣减是按平台数扣 `cloud_publish` 次数（3 处调用，全硬阻断）。

3. **成本链路在最后一跳断了**。`_writeLog()` 不传 `tokens_in / tokens_out / cost`，导致 `model_usage_daily.cost` 恒为 0。`cost_per_1k_tokens` 字段存在，但**没有任何一处拿它做乘法**。也就是说：**平台自己也不知道花了多少钱。**

4. **视频模型连计费原料都拿不到**。adapter 响应只返回 `{taskId}` / `{status, videoUrl, progress}`，时长和分辨率仅存在于请求侧。必须用「请求侧记账 + 回执兜底」双写。

5. **fallback / 轮转代码存在但生产不可达**。`ProviderRouter` 实现了 `round_robin` / `failover` / `excludeIds`，但唯一入口要 `params.useFailover === true`，而该标志在生产代码里**零命中**。当前所有模型调用都是**单点，无备份**。

6. **建议赠送量：标准版 1000 积分 / 专业版 2200 积分**（1 积分 = ¥0.01 上游成本）。现状的 500 / 3000 是**标准版偏少、专业版超卖约 2 倍**。另外发现一个硬矛盾：**年付 ¥199 在「月清零 + 每月发 1000 积分」下数学上无法盈利**，必须改成按季发放 + 可结转（详见 §7）。

### 更重要的发现：代码里**没有营销价机制**

按 `promo / discount / coupon / early_bird / marketing_price / sale_price / half_price / 限时 / 优惠 / 促销 / 半价 / 早鸟 / 特价` 全仓检索
（`packages/api-publish-engine/src`、`ops-center/backend`、`migrations/`）：

> **零命中（仅 3 处无关命中：body size 限制文案、AI 味替换词表、rewrite prompt 模板）。**

**即：`plan-matrix.js` 里的 ¥29 是系统里唯一的价格，没有「正价」这个概念，更没有营销活动的数据结构。**

如果直接把 `priceMonthlyCents` 改成 `5900`，**推广期半价就没有地方承载**——你会在结账时发现没法按 ¥29 收款。

### 三条结构性结论

**① 赠送量必须按「正价」计算，不是按营销价。**

赠送额度的成本是**已发生且不可回收**的。用户半价付了 ¥29，你发 2000 积分的成本仍是 ¥20，成本占比 69%。

若按营销价 ¥29 反推赠送量，再套用到正价用户身上，等于**正价用户在补贴半价用户**——这是最不健康的一种价格歧视。

**② 但营销期不能按正价发同样的积分，否则营销期直接亏穿。**

正确的做法是**营销期降赠送量，而不是营销期送双倍**：

| | 售价 | 赠送积分 | 月成本 | 成本占比 |
|---|---|---|---|---|
| 正价期 | ¥59 | **2000** | ¥20 | **33.9%** ✅ |
| 营销期 | ¥29 | **1000** | ¥10 | **34.5%** ✅ |
| （若营销期也送 2000） | ¥29 | 2000 | ¥20 | **69%** ❌ |

**两期成本占比基本一致 → 营销的实质是「降价 + 减配」，不是「降价送双倍」。**

**附带一个好处**：营销期用户已经习惯了 1000 积分，正式期升到 2000 是**权益增加的正向惊喜**；反过来如果营销期就给 2000，正式期涨价后用户什么也没多拿，营销就只剩「便宜」这一个意义。

**③ 年付折扣与成本占比之间是数学锁死的，无法靠设计绕开。**

```
年付成本占比 = 月付成本占比 ÷ (1 − 年付折扣)
```

- 折扣 15% → 41.2%
- 折扣 20% → 43.8%
- 折扣 29.5% → **49.6%**
- 折扣 30% → 50%

**你不可能同时要「年付打 3 折」和「年付成本占比仍保持 35%」。**



| # | 你的原始主张 | 判定 | 修正建议 |
|---|---|---|---|
| 1 | 两档都能用官方内置模型，算力换算成积分消耗 | ⚠️ **有条件成立** | 必须引入 `tier_access` 分层，否则「更贵档位可用所有功能」这个卖点塌成只剩配额差异，且高成本模型被低档白嫖。**低成本模型全档开放，高成本模型仅 pro 可用。** |
| 2 | 不同档位每月赠送不同积分 | ✅ **成立，但数字要改** | 500 / 3000 → **1000 / 2200**（见 §6） |
| 3 | 不同档位有不同的功能限制和数量限制，贵档可用所有功能 | ⚠️ **数字存在，校验不存在** | `maxPlatforms` / `dailyPublish` / `concurrentTasks` **零校验**，且客户端 `normalizeEntitlement()` 直接把 `limits` 字段丢弃。这三个值现在连客户端内存态都进不去。 |
| 4 | 用户可设置自己的模型，不消耗积分 | ✅ **成立** | BYOK 只免算力积分，**功能配额照旧受会员档约束**。这样会员差异才有意义，否则成熟用户全部 BYOK + 买最低档。 |

## 三、功能 → 成本 → 积分映射表（核心）

### 3.1 计费边界原则

> **只有「生成」扣积分，「操作」不扣。**

| 类别 | 是否扣积分 | 说明 |
|---|---|---|
| AI 改写 / 润色 / 标题 / 摘要 / 标签 / 分镜脚本 | ✅ 扣 | 按 token |
| AI 生图（封面 / 分镜配图 / 素材） | ✅ 扣 | 按张 × 分辨率档 |
| AI 视频生成 | ✅ 扣 | 按秒 × 分辨率档 |
| TTS 配音 | ✅ 扣 | 按计费字符 |
| ASR 转录 | ✅ 扣 | 按音频秒 |
| Embedding / 质量评估 | ✅ 扣 | 按 token（极低，可给免费额度） |
| 账号绑定与登录态维护 | ❌ 不扣 | 平台能力 |
| 发布 / 排期 / 定时批量 | ❌ 不扣 | 平台能力 |
| 数据统计 / 素材库 / 发布历史 / 失败重试 | ❌ 不扣 | 平台能力 |

**心智模型一句话**：会员费买平台能力，积分买 AI 用量。

### 3.3 积分换算公式

```
积分消耗 = ceil( 用量 × 单价 × 上游采购折扣系数 × 100 )     # 1 积分 = ¥0.01
```

**取整规则**：

- 文本：向上取整到 **0.1 积分**，最低 **1 积分**
- 生图：向上取整到 **1 积分**
- 视频：向上取整到 **5 积分**（避免秒级误差累积）
- TTS：向上取整到 **0.5 积分**
- **失败 / 超时 / 中途取消：不扣**（判据是上游是否真的返回了有效产出，不是用户点没点取消）

**上游采购折扣系数**：如果你是走中转商套餐拿到 8 折，把系数设为 0.8——**这一项是防亏的关键参数，必须做成后台可配，不能硬编码。**

### 3.4 套餐成本摊销（Q9 已定：混合制）

| 阶段 | 判定 | 摊销方式 |
|---|---|---|
| 保底期 | 套餐剩余 > 50% | 等效单价 = 套餐总价 ÷ 套餐总额度，**月内固定** |
| 接近耗尽 | 套餐剩余 20%–50% | 单价上浮至等效单价的 **1.2 倍** |
| 濒危 | 套餐剩余 < 20% | 单价上浮至 **1.5 倍**，并向运营告警 |
| 耗尽 | 剩余 = 0 | **自动切聚合 API**，单价按聚合 API 实时价重算 |

**这一段专门防「月末薅」**：纯等效单价会让用户在你套餐最贵的时间点集中跑视频。

```sql
  ON model_price_cards(provider_id, model_id, action_type, spec, quality_tier, effective_from);
```

**关键设计**：`effective_from / effective_to` 支持**价格历史**。上游调价时插入新版本，历史账单仍能按当时价重算——这是「不追认」的底线。

### 4.2 新增 `generation_request`（解决 G5：视频无原料）

```sql
-- 生成请求台账：请求侧记「应有成本」，回执记「实际成本」
CREATE TABLE generation_requests (
  id              UUID PRIMARY KEY,
  user_id         TEXT NOT NULL,
  client_id       TEXT NOT NULL,
  action_type     TEXT NOT NULL,     -- 'video'|'image'|'tts'|'llm'|'asr'
  provider_id     TEXT NOT NULL,
  model_id        TEXT NOT NULL,
  spec            TEXT DEFAULT '',   -- 请求的分辨率
  duration_sec    NUMERIC(8,2),      -- 请求的时长（视频/TTS/ASR）
  count           INT DEFAULT 1,     -- 张数
  prompt_chars    INT DEFAULT 0,     -- 文本类
  upstream_task_id TEXT,             -- 上游 taskId，用于回填
  expected_cost   NUMERIC(12,6) NOT NULL DEFAULT 0,  -- 请求侧算的成本
  actual_cost     NUMERIC(12,6),                      -- 回执/账单回填
  actual_usage    JSONB,             -- 上游回执原文
  credits_charged INT NOT NULL DEFAULT 0,
  status          TEXT NOT NULL,     -- 'reserved'|'completed'|'failed'|'refunded'
  tier            TEXT,              -- 'standard'|'hd'|'cinema'（质量档，非模型名）
  degraded_from   TEXT,              -- 若发生降级，记录原模型
  created_at      TIMESTAMPTZ DEFAULT now(),
  settled_at      TIMESTAMPTZ
);
CREATE INDEX idx_gen_user_time ON generation_requests(user_id, created_at DESC);
CREATE INDEX idx_gen_status     ON generation_requests(status) WHERE status <> 'completed';
```

**工作流（借鉴 `cost_tracker.py` 的预留范式）**：

```
提交生成
  ├─ 服务端查 ModelPriceCard → 算 expected_cost → 扣积分（status='reserved'）
  ├─ 落 generation_requests 一行
  ├─ 调上游，拿 upstream_task_id 回填
  ├─ 轮询 / 回调
  │    ├─ 成功：从回执解析 usage → 算 actual_cost → 按实际退差额
  │    ├─ 失败：全额退积分（status='refunded'）
  │    └─ 超时（10 分钟硬超时，见 story2video-stages.js:752）：按上游实际扣
  └─ 每日 03:00 对账：expected_cost vs actual_cost 差异 >15% → 告警
```

**「应有 vs 实际」的差异本身就是探针**：它会自动发现 adapter 少传参数、上游悄悄涨价、或某个模型的账单口径变了。

## 五、发放节奏与重置规则

### 5.1 日释放 + 月清零（Q10 已定）

```
每日 00:00 释放  月度总量 / 当月天数
月末 23:5959 未用完 → 清零（会员额度）
充值积分     → 不受日释放限制，永久有效，优先在会员额度耗尽后才扣
```

**为什么不是月初一次性发**：纯一次性会被「每月 1 号 0 点全量生成」打穿——一个号一天能吃掉全年赠送量的 1/12。**日释放平抑峰值薅，月清零不留套利空间。**

**扣减优先级**：先扣即将过期的（会员额度日释放部分）→ 再扣本月剩余 → 最后扣充值积分。

### 5.2 年付的数学矛盾（重要发现）

> **在「月清零 + 每月发 1000 积分」的前提下，标准版年付 ¥199 数学上无法盈利。**

```
年成本 = 1000 积分/月 × 12 × ¥0.01 = ¥120
收入   = ¥199
算力成本占比 = 60.3%     ← 目标 35%，超卖 1.7 倍
```

要维持 35%，年付价必须 ≥ ¥343（比现价高 72%，年付失去意义）。

**这不是设计能绕开的**——年付折扣 42.8% 意味着收入少 43%，而「月清零」又强迫用户把额度用满，成本一分不省。

**推荐解：年付改按季发放 + 余额可跨季结转**

| | 季度发放 | 年最大消耗 | 年最大成本 | 占比 | 预期实际消耗占比 |
|---|---|---|---|---|---|
| 标准版年付 ¥199 | **2000 积分/季** | 8000 | ¥80 | 40.2% | **20–30%** |
| 专业版年付 ¥599 | **4400 积分/季** | 17600 | ¥176 | 29.4% | **15–21%** |

**结转是关键**：不结转 = 用户被迫用满；结转 = 你按用户实际消耗付费，毛利由行为决定而非清零机制强迫。而且沉没余额本身就是留存粘性。

**宣传口径**：年付的卖点写成「**锁定当前价格 + 权益不变**」，不要写「年付送更多积分」。

## 六、赠送量测算与最终建议

### 6.1 计算过程

```
赠送量 = 会员月费 × 目标成本占比 ÷ ¥0.01（单积分成本）

标准版正价：¥59 × 35% = ¥20.65 → 2065 → 取整 2000 积分
专业版正价：¥79 × 28% = ¥22.12 → 2212 → 取整 2200 积分
```

### 6.1b 最终定价表（v1.2 修正版 — 年付积分 = 月付 × 12）

> **硬约束（用户指定）**：年付积分必须与月付完全一致，**不允许年付少拿**。
> 专业版**单一价格**，无正价/推广双轨。
> 这条约束把月付赠送量的上限锁死了，推导如下。

**推导**

设月付赠送量 = M 积分（成本 = 0.01M 元）：

```
月付成本占比  = 0.01M / 月付价
年付成本      = 0.12M              （因为年付给 12M 积分）
年付成本占比  = 0.12M / 年付价
```

**在「年付折扣 ≥ 25%」的前提下**（年付没有 25% 以上折扣就没人买），解出 M 的上限：

| | 月付价 | 年付折扣 | 年付价 | M 上限 | 取整 |
|---|---|---|---|---|---|
| 标准版 | ¥59 | 30% | ¥499 | 0.12M ≤ 499×0.40 → **M ≤ 1663** | **1600** |
| 专业版 | ¥79 | 26% | ¥699 | 0.12M ≤ 699×0.40 → **M ≤ 2330** | **2200** |

> **「年付成本 ≤ 40%」是这条约束的代价**。如果年付成本占比能接受 45%，
> 标准版月付可以给到 2000 积分（38%）。我建议守 40% —— 现在防亏三道闸全缺，起点该保守。

**最终定价表**

| 档位 | 周期 | 售价 | 赠送积分 | 成本 | 成本占比 | 年付折扣 |
|---|---|---|---|---|---|---|
| 免费版 | 月 | ¥0 | **30** | ¥0.30 | — | — |
| **标准版** | **月付（正价）** | **¥59** | **1600** | ¥16.00 | **27.1%** | — |
| **标准版** | **月付（推广期）** | **¥29** | **800** | ¥8.00 | **27.6%** | — |
| **标准版** | **年付** | **¥499** | **19200**（=1600×12） | ¥192.00 | **38.5%** | **29.5%** |
| **专业版** | **月付** | **¥79** | **2200** | ¥22.00 | **27.8%** | — |
| **专业版** | **年付** | **¥699** | **26400**（=2200×12） | ¥264.00 | **37.8%** | **26.3%** |

**校验（全部通过）**

```
年付积分一致性：
  标准版  1600 × 12 = 19200  = 年付积分  ✅
  专业版  2200 × 12 = 26400  = 年付积分  ✅

年付折扣：
  标准版  (59×12 − 499) / (59×12) = 209/708 = 29.5%  ✅
  专业版  (79×12 − 699) / (79×12) = 249/948 = 26.3%  ✅

单位积分成本（年付应显著低于月付）：
  标准版  月付 59/1600 = ¥0.0369   年付 499/19200 = ¥0.0260   → 年付便宜 29.6%
  专业版  月付 79/2200 = ¥0.0359   年付 699/26400 = ¥0.0265   → 年付便宜 26.2%
```

**⚠️ 专业版年付从 ¥599 调整为 ¥699（+16.7%）**。必须调，因为现状 ¥599 下发 26400 积分 = 成本 ¥264，**成本占比 44.1% 已超卖**。现在真实支付尚未接通、没有存量年付用户，**这是零成本调整的窗口期**；接了支付再改就要处理退差价了。

**推广期设定**：标准版 ¥29 / 800 积分。800 是 1600 的一半，**两期成本占比对齐在 27% 附近**（27.1% vs 27.6%）——营销的实质是「降价 + 减配」，不是「降价送双倍」。

**免费版给 30 积分**：约 2 条 720P 视频或 7 张标准清晰度图，够用户体验一次完整流程再决定要不要付费。

### 6.2 与现状对比

| 档位 | 现状积分 | 建议积分 | 变化 | 现状成本占比（按正价） | 建议成本占比 |
|---|---|---|---|---|---|
| 免费版 | 0 | **30** | 新增 | — | — |
| **标准版** | 500 | **1600** | **×3.2** | ¥5 / 59 = **8.5%** | ¥16 / 59 = **27.1%** ✅ |
| **专业版** | 3000 | **2200** | ×0.73 | ¥30 / 79 = **38.0%** | ¥22 / 79 = **27.8%** ✅ |

**现状的问题很清楚**：
- 标准版 500 积分 = **3 条** 720P 短视频，只发了 8.5% 的成本预算——**等于把算力白送**，用户还觉得买少了。新方案 ×3.2，且成本占比从 8.5% 提到 27.1%。
- 专业版 3000 积分 = 20 条 720P 视频，成本 ¥30 占 38%——**已经在超卖**，且高成本模型敞开用，实际更差。新方案降到 2200。

**新方案**：两档月付成本占比统一在 **27–28%**，便于统一管理和对账。**档位差异全部落在功能配额和模型分层上**——这正好与「BYOK 只免算力、功能配额受档位约束」的决策一致。





### 6.3 内部测定期（支付未接通）的降级口径

> ⚠️ 放开时注意：**年付必须同步从 7200/9600 提到 19200/26400**，保持「年付 = 月付 × 12」的一致性。

## 十一、假设与待验证项

> 本节是本报告的**可信度边界**。以下内容请勿当作已验证事实使用。

| # | 假设 | 影响 | 怎么验证 |
|---|---|---|---|
| 1 | **所有单价为 2026-10-08 公开挂牌价**，非你的实际采购价 | 直接影响赠送量准确性 | 拉近 30 天上游账单，反推真实加权单价，回填 `ModelPriceCard` |
| 2 | **未计入支付通道费**（支付宝/微信约 3–5%） | 成本占比会略高于 35% | 从收入端倒扣 |
| 3 | **未计入账号维护成本**（养号、封号应对、登录态） | 这是实际最大成本项 | 需要你的运营台账 |
| 4 | **未计入推理重试率** | 实测重试率常在 20–40%，会显著抬高真实成本 | 上线后从 `generation_requests` 的 `expected vs actual` 观测 |
| 5 | **未计入失败成本**（上游失败的调用可能仍计费） | 视频/生图常见 | 同上，按上游账单核对 |
| 6 | 假设重度用户月消耗占其赠送量 >90% | 决定均值是否失真 | 上线 30 天后看 P75/P95 分布 |
| 7 | **免费版 `officialCreditMonthly: 0` 是否合适** | 若为 0，用户完全无法试用内置模型 | 建议给 **30 积分体验额度**（够 2 条 720P 视频或 7 张图），但不给 `video_create` feature |
