> 分析日期：2026-10-06
> 分析基线：`01-docs/PRD.md`（PROJECT-003，v2.3.60）+ 130 份子 PRD + `marketing/01-产品卖点清单.md`（66 条卖点）+ `marketing/03-用户痛点地图.md`（4 类人群）

> 方法：文档逐条对照代码取证。**所有结论标注了 `file:line` 证据；spec 存在不等于功能已实现，本报告只认 `src/` 里的代码和 `migrations/` 里的真实表结构。**

## 〇、一句话结论

**这个项目不缺功能，缺的是「对外承诺」和「产品实况」之间的对齐。**

- 66 条卖点里 60 条标着「待核实」，实际查完代码：**约 20 条已经是可以对外讲的硬能力**（自带模型 Key、15 平台注册表、7 态审核状态机、失败重试、频控、采集反爬策略层、质量四维评估……）。
- 但同时查出 **12 处卖点与代码直接矛盾**，其中 **8 处一旦说错就是信任事故**：
  `买一次没有月费` / `数据都在本地` / `绝不会串号` / `花了多少你看得见` / `周末备货自动发` / `掉线马上知道` / `博主作品一键入库` / `订阅对标博主`。
- **另外两条不是话术问题，是架构和经营问题，改话术救不了**：
  **A11** 采集合规与版权（stealth 绕过反爬 + 视频下载转写他人作品 + 数据里没有作者）；
  **A12** Windows 构建完全未签名 + 发布者是个人 GitHub 账号——**这意味着"凭证在你本机"这条核心信任的物理基础是整个更新通道**。
- **专项深审还挖出第三层问题（第三节）**：不只是"说大了"，有几条是**说小了但同时做不到**——去 AI 味 33 条模式里 32 条只检测不修复、音画对齐的 ASR 结果在成片阶段被丢弃、批量改写绕开了主引擎、多版本/多比例/成本可见完全没做。**这些不是话术问题，是产品债。**
- 痛点地图反复追问的「矩阵团队六问」，现在能答上 5 问，**答不上来的 2 问（操作审计、团队权限）代码里确实一个字都没有**——这是付费主力真正的入场券缺口。
- **正面结论也有，别只盯着问题**：凭证加密是真 fail-closed（拒绝明文降级）、云端配置下发有 Ed25519 验签、Python sidecar 独立进程有界重启（单平台崩不拖垮全应用）、无硬编码密钥无后门。**这几条是可以正面讲的硬差异点。**
- 所以优先级应该是：**先止血（修话术）→ 再补债（定时常驻 / 去 AI 味 / 音画对齐）→ 再补牌（审计 + 权限）→ 最后才是加功能**。而 **A11 / A12 要单独拉出来拍板，不排进任何批次**。

## 一、关键发现 A：十二处话术错位 + 两条架构与经营问题

这一节是本次分析最紧急的产出。**这十二条不是"缺功能"，是"现在对外说的话和产品实际行为不一致"。** 其中 A11（采集合规）是经营风险、A12（未签名更新）是安全架构问题，**这两条都不是改话术能解决的**。

### A1 · 平台数量对外说少了，但"7 个后台"的痛点话术要重写

| 项 | 文档说法 | 代码事实 | 证据 |
|---|---|---|---|
| 支持平台数 | **7 个**（百家号/快手/B站/抖音/公众号/头条/视频号） | **15 个**，含 5 个海外平台 | `packages/shared-utils/src/publish-capabilities.js`（实测 `Object.keys()` = 15：`wechat_mp, zhihu, weibo, douyin, xiaohongshu, tencent_video, kuaishou, toutiao, bilibili, baijiahao, youtube, tiktok, twitter, instagram, facebook`） |

- 注册表由 `publish-capabilities.test.js:42` 钉死「覆盖全部 15 个支持平台，无缺失无多余」，**改平台数会被测试拦住**——这是好事，说明有单一真源。
- **风险不是"说少了"（少说安全），而是痛点话术失效**：痛点地图全篇用「开 7 个后台传 7 次」建立共鸣。实际用户开的是 15 个后台，**痛点比文档描述的更重，话术应该往上调而不是往下调**。
- 建议：S-11 改为「一次创作，15 个平台一起发」；痛点锚点从「7 个后台」改为「十几个后台」。

### A3 · 三个核心卖点对免费版和标准版不成立

`ops-center/docs/pricing-strategy.md` §2.2 写的是：批量操作 **免费 ❌ / 标准 ❌ / 专业 ✅**，发布平台 **1 个 / 3 个 / 全部**。

而 `plan-matrix.js`（更新更晚，2026-09-23）写的是 `maxPlatforms` **5 / 15 / 不限**。**两份文档已经漂移了**——这本身就是个问题（`plan-matrix.js:5` 声明自己是"服务端唯一真源"，但对外文档没跟上）。

无论按哪一版，结论都一样：

| 卖点 | 对免费版 | 对标准版 | 说明 |
|---|---|---|---|
| **S-05** 批量改写 | ❌ | ❌ | 按 pricing 文档，免费+标准都无批量 |
| **S-11** 一次创作 7 平台同发 | ⚠️ 只有 5 个平台 | ✅ | 免费版封 5 平台 |
| **S-18** N 号 × 7 平台矩阵铺量 | ❌ | ❌ | 批量 + 并发 1/3，矩阵场景基本不成立 |
| **S-37** 漏发可见/重试 | ✅ | ✅ | 这条不设限 |
| **S-42** 「加号只是加点的事，没有硬上限」 | ❌ | ⚠️ | 免费版 `dailyPublish: 5` 是硬上限 |

**建议**：卖点清单必须**按档位重写**。现在这套卖点是按"专业版"写的，但投放素材面向的是"几百块能试"的个人创作者（痛点地图原话）。**用专业版的能力卖免费版的价格，是最容易收到差评和退款的一条路径。**
### A4 · 「数据都在本地」需要按当前代码路径收窄措辞 🔴

> ⚠️ **本条在 v4 再次修订。** v4 我把「凭证信封加密上云」当成正面证据列进表格——**那是服务端侧的加密，客户端上行是明文**。我当时的判断不完整，这里更正。

| 文档说法 | 代码事实 |
|---|---|
| S-21：「你的素材库、账号信息、草稿都存在你自己电脑上」 | 账号**元数据**是本地真源；**登录凭证在用户显式点击同步时以明文上行**（TLS 内传输），由**服务端**加密落库；下行时服务端**解密后明文返回** |
| — | 平台有「官方内置 Key 池」，`ops-center/backend/models.py:116-137` `official_keys` 表，**Fernet 加密存储** |

**凭证同步链路的真实形态**（代码注释原文，`packages/api-publish-engine/src/cloud-accounts/handlers.js:220`）：

```js
// 上行是明文凭证（PRD §7.2 / ADR-0003：加密发生在服务端，桌面端没有也不该有 KMS 访问权）。
// 缺 crypto 一律 503 fail-closed，绝不存在「没有 KMS 就明文入库」的降级分支。
```

即：**客户端 → 服务端 = 明文（TLS 内）→ 服务端 KMS = 加密存储 → 下行 = 服务端解密后明文**。
这是 ADR-0003 的**显式设计**（"换设备免扫码 ⇒ 服务端必须能重新解出凭证"）。`CONTEXT.md:40` 说的"本机主密钥永不上云"指的是**本地那把**，云端另有一把服务端主密钥。

**🔴 界面文案不准确（必须改）**

用户实际看到的是（`apps/desktop/src/locales/accounts-cloud-sync/zh.js:26`）：

> 「登录凭证将**加密后**上传；可在需要时一键清除云端数据」

**实际是「上传后由服务端加密」。** 传输层有 TLS（不是裸奔），但这句话会让用户以为"我们拿到的是密文"——**属于披露不准确**。

**🚫 绝对不能说**：**「凭证不出本机」** / 「内容不过第三方」 / 「端到端加密」

**建议措辞**（现在能说的版本）：

> 「你的**账号和素材**默认存在你自己的电脑上。开启云同步后，登录凭证会通过加密通道上传、由服务器加密保存——这是为了让你换电脑时不用重新扫码。你可以随时一键断开并清除云端数据。」

**✅ 能放心说的部分**（这些是真的，v4 结论不变）：

| 证据 | 位置 | 说明 |
|---|---|---|
| **本机凭证加密是 fail-closed** | `crypto.js:80-100` | safeStorage 不可用时 encrypt/decrypt **直接 throw**，注释明写「refusing plaintext fallback」。`credential-store.js:84-89,158-163`、`ops-center-sync.js:183`、Python 侧 `douyin_auth.py`/`bilibili.py`/`xiaohongshu_auth.py` **全部一致** |
| **服务端 KMS 缺失也 fail-closed** | `handlers.js:220-226` | 缺 crypto 一律 503，**绝无"没有 KMS 就明文入库"的降级分支** |
| **模型用量上报不含内容** | `usage-reporter.js:103-146` | 只发 `client_id / provider / category / action / latency / tokens / cost`，**无任何正文字段** |
| **无硬编码密钥 / 无后门** | 全仓扫描 | `config.yaml` 均为 `${VAR}` 占位符；ops-center 弱口令闸门三重 fail-closed 且已接线到启动事件；全仓无 `BACKDOOR`/`god_mode`/`disable_auth` 类开关 |
| **云端配置下发有验签** | `ops-center-sync.js:91-113` | **Ed25519 签名验签，失败即拒绝应用任何策略**；禁重定向、强制 HTTPS、≤1MB、10s 超时、`Cache-Control: no-store` |

> 📌 **S-62「凭证加密存储」和 S-28「自带 Key」仍然站得住**——尤其"拒绝明文降级"，竞品基本没人敢写。
> 📌 **但"官方积分 / LLM Router 上线"这条风险要绑定处理**：一旦平台内置 Key 下发（`pricing-strategy.md` §1 自述其隐私属性是「平台可见」），**内容就经过平台**，届时 S-21 必须再改一次。

### A5 · 「绝不会串号」现在不能这么说（但理由要改） 🔴

> ⚠️ **本条已在 v4 更新**。深度审计发现**账号维度并发隔离其实已经落地 main 了**（我 v3 说的"正在修"偏保守）。问题不是"没做"，而是"只做了一层，有两个可复现的绕过路径"。

**已落地的部分**（我已复核）：

```js
// packages/shared-utils/src/task-queue.js:485-487
_channelKey (task) { return task.platform + ':' + (task.accountId ?? '') }
// :495  _runningByChannel 记账（在第一个 await 之前，同步生效）
// :471-474  同通道在跑 → 留队轮候，继续扫后续任务
```

配套的 RPA 窗口池（`rpa-view-session.js:130-165`，池大小 6 / TTL 10 分钟）、抖音图文去固定 sleep、抖音图文 API 链，**B/C/D/A2 四项全部已在 main**。

**但防御只有一层，两个绕过路径真实存在**：

| 绕过路径 | 机制 | 触发条件 |
|---|---|---|
| **① 空 accountId vs 显式默认账号** | `task-queue.js:158` 只取任务级字面值，空值归一为 `''`（通道键 `wechat_mp:`）；而 `publisher-router.js:370-374` **到发布时刻**才回退默认账号并回填 `article.accountId`。于是「无账号任务」与「显式指定该默认账号的任务」通道键不同，**却解析到同一个 `persist:rpa-*` partition** | 主进程 `publish.js:282` 允许 `accountId: ''`（只校验 `isSafePathSegment` 格式，不校验非空）；渲染层有守卫，主进程没有 |
| **② 窗口池无 in-use 守卫** | `rpa-view-session.js:134-144` `_acquireWindow` 只做「命中就取出、未命中就新建」，**没有"该 key 正被别的任务持有"的检查**。防双开完全依赖 TaskQueue 那一层 | 任何绕过 TaskQueue 直接调 `rpaViewManager.publish` 的路径 |

**另外**：进度路由仍是 `platform` 单键 last-write-wins（`publish-progress-events.js:198-213`，注释自认"已知近似"）——跨账号同平台并发时进度会串。

**结论**：S-39「串号这种事我们不允许发生」**仍然不能说**——不是因为没做，而是因为**有已知可复现的缺口**，一旦被客户撞上就是事故。**改法也不变**：

> 「同一账号在同一平台的发布任务由队列强制串行；每个账号独立的登录环境，A 号的草稿不会出现在 B 号的草稿箱。」

**解锁强话术的条件**：主进程补 `accountId` 非空校验（或在通道记账前先解析默认账号）+ `_acquireWindow` 补 in-use 守卫 + 补同账号串行回归测试。**三者都做完，才敢说"不会"。**

### A6 · 「花了多少钱你看得见」目前是零基础 🔴

| 文档说法 | 代码事实 |
|---|---|
| S-46：「模型调用按量付费，用多少花多少，**花了多少你自己看得见，不会有账单惊吓**」 | **全链路没有任何 token / 金额统计** |
| S-46 在痛点地图里是**代运营的收尾话术**（「收尾：S-19/S-46 少雇一个人」） | 用户侧看板成本字段**硬编码为 0** |

**代码侧证据**：
- `grep tokens_in|prompt_tokens|usage` 在 `packages/rewrite-engine/src`、`packages/ai-writer/src` → **零命中**，改写链路根本没记 token
- `apps/desktop/electron/services/board-service.js:143` → `cost: 0` 写死
- `apps/desktop/electron/services/pipeline-engine.js` 里的 `estimatedCost: 'low' / 'medium' / 'high'` 是**静态枚举字符串**（预设的"低/中/高"档位标签），不是算出来的钱
- 唯一真实的用量统计在**平台侧**：`ops-center/backend/models.py:215` `ModelUsageDaily`（日聚合，`ops-center/backend/models.py:250` `ModelUsageBatch`），但它记的是**调用次数 + 延迟分桶**（`latency_buckets: {"lt1s": n, "1to3s": n, ...}`），**没有金额字段**

**换句话说**：平台知道花了多少钱（`official_keys.cost_per_1k_tokens`、`alert_threshold_cost` 在 `ops-center/backend/models.py:128,134`），**用户不知道**。

> 🔍 **v4 追加发现（我已实测）**：**平台其实也不知道。**
> `usage-reporter.js:85` 从本地 provider 日志表取数，`:109,123-124` 累加 `tokens_in/tokens_out`，但**源表 `model-provider-manager.js:359-366` 从不填这些列**——所以上报到 ops-center 的 `tokens_in/tokens_out/cost` **恒为 0**。
> 也就是说：**`ops-center` 的 `ModelUsageDaily` 表里，成本数据也是全零**。定价策略里那套"按 Provider 成本估算、按日配额、成本告警阈值"的机制，**目前拿不到真实数据支撑**。
> **这条要同步告诉运营**：如果已经在按"官方积分亏损率"做决策，那数据基础目前是不存在的。

**为什么这条要立刻改**：S-46 是痛点地图里给代运营的**收尾杀手锏**——"成本可算"，是代运营向客户证明工具划算的支点。**这条现在讲不了。**

> 补充一条对 A4 有利的好消息：`ModelUsageDaily` 的注释明写「**桌面端脱敏上报**，运营后台看板数据源」，唯一键是 `(usage_date, client_id, provider_id, action)` + 延迟分桶——**上报的是调用元数据，不含用户内容**。这是 A4「内容不过第三方」那句话目前能拿到的正面证据。

**修复成本很低**：改写/生成链路把 `usage` 从 LLM 响应里透出来落库，客户端加一行"本月用量与折算金额"。**这是全表里"对外收益大 / 实现成本低"的少数几条之一。**

### A7 · 「周末备货，工作日自动发」有个大前提没说 🔴

S-13 卖的是「攒好的内容批量排期，到点自动发」。**但定时发布是纯 Electron 主进程内存定时器，没有任何系统级或云端兜底。**

| 场景 | 实际行为 | 证据 |
|---|---|---|
| 应用退出 | **不发**。`scheduler.stopAll()` 清空全部定时器 | `shutdown.js:50-52` |
| 排期跨越重启 | 重启后**立即补发**过期未发的任务 | `scheduler.js:266-270`（`remaining <= 0` 直接 `startDispatch`）、`phase3-services.js:260` |
| **关窗口但不退出** | ⚠️ **只有托盘可用 + 有运行中/排队任务时才拦截关闭**。**空闲状态下关窗口 = 直接退出进程，定时任务随之停摆** | `window.js:155-166`（`hasRunningPublish = running + queued > 0`） |

**为什么这条对代运营是硬伤**：他们的核心用法就是「周一到周五自动铺，周末休息」——**这恰恰是"空闲状态"**。用户周一到周五下班关窗口，定时就断了。**卖点的使用场景和产品行为正好相反。**

**改写后**
> **一句话**：软件开着（含最小化到托盘）时会按时发；关掉软件不会发，下次启动会把过期的补上。

> 📌 **这是本次分析里最值得投入的一个修复**：加一个系统级常驻（Windows 计划任务 / 托盘自启 + 心跳）成本不高，但它**直接决定代运营能不能真的按订阅付费**——按月付钱买的是"持续发"，软件一关就断是要退款的。

### 3.2 四个必须知道的深坑

#### 坑 1 · 去 AI 味：检测器越完备，越容易给人"已处理"的错觉

`ai-taste-remover.js` 的 3-pass 架构是真的，但**检测与修复严重不对等**：

- `STRUCTURE_PATTERNS` 22 条（`:187-342`）+ `TONE_PATTERNS` 11 条（`:347-425`）**全部只被 `detect()` 消费**
- `_fixStructures()`（`:802-818`）实际只做两件事：删禁用开头、删连接词后逗号
- 实跑验证：`首先…其次…最后`（三连排比）、`希望这对您有帮助…`（聊天残留）、`赋能/抓手/闭环`（商业黑话）、`这不仅仅是…而是…` —— **全部原样穿透，命中数处理前后不变**

**更严重的是这个**（`:875-896`，我已逐行复核）：

```js
// 注释写的是：「前句终止标点改逗号衔接，后句保留自身标点」
const head = sentences[i].replace(/[。！？；!?;]+$/, '')  // 剥掉 ？！
result.push(head + '，' + sentences[i + 1])              // 却接逗号
```

**设计意图是明确的**（消除句长雷同），但对 `？` 和 `！` 会造成语义破坏——实跑：

```
IN : 难道你不想成功吗？这样做难道不对吗？大家怎能不心动呢？
OUT: 难道你不想成功吗，这样做难道不对吗？大家怎能不心动呢？
```

**反问句被改成了陈述句。** 守卫条件只有长度（合计 < 80）和 ±20% 长度差，**不检查标点类型**。

> 定性：这是一个**有意的设计带来的非预期后果**，不是随手写错。但它的对外后果和 bug 一样——用户看到自己的反问句被改成陈述句，第一反应是"这工具会毁我的文案"。
> **修法很轻**：合并前判断标点类型，`。` 可合、`？`/`！` 不合。改动量大约 3 行。

**第三条**：全程确定性，**零随机**。测试 `ai-taste-remover.test.js:162` 甚至把「键序确定」锁成了契约。这意味着**即使将来做了多版本产出，所有版本的去 AI 味结果也会高度同质**——而"避重复"正是多版本的目的。

#### 坑 4 · 自动重试零退避 + 几乎所有错误都重试（发布链路）

这条是**产品缺陷，不是话术问题**，但后果直接砸在"稳不稳"这个矩阵团队第一问上。**我已逐行复核。**

```js
// packages/shared-utils/src/task-queue.js:580-585
if (!e.noRetry && task.retriesLeft > 0) {
  task.retriesLeft--
  task.status = 'pending'
  this.emit('task:retry', task)
  this._queue.push(task)   // ← 裸 push，无任何延时
}
```

**两个问题**：

1. **零退避**：失败后**立即**回队尾重打平台。真实网络抖动下这是最糟的策略——平台刚返回失败就立刻再打，很容易撞限流甚至触发风控。全文件在重试路径上没有任何 `setTimeout` 或退避计算。

2. **`retryable` 判据形同虚设**：唯一判据是 `!e.noRetry`，而 **`noRetry` 全仓只被设置过 1 次**——`risk-suspender-store.js:33`（风控即停）。于是：
   - 认证失败（Cookie 缺失）→ **重试 2 次**
   - 内容审核被拒 → **重试 2 次**
   - 平台 4xx 参数错误 → **重试 2 次**

   这些重试**毫无意义**，只是白打平台两次。

> 讽刺的是：`adapters/_base/provider-error.js:29-42` 有一张**完整的 `retryable` 元数据表**（`AUTH_FAILED:false` / `RATE_LIMITED:true` / `QUOTA_EXCEEDED:false` …），**但发布主链路根本不经过它**，只被 `zhihu-favlist.js` 等旁路使用。

**好消息**：一条失败**不会阻塞整批**（`batch-manager.js:345-380` 逐任务隔离 try/catch，`acceptedTasks` Map 按 taskId 归属结算）。

**修复方向**：① 接退避（指数 + 抖动）；② 把 `provider-error.js` 的 `retryable` 元数据接进发布主链路；③ 认证/参数类错误设 `noRetry`。

| 词库可运营 | 「AI 味词库支持后台 CRUD、导入导出、实时下发」 |
| 流水线稳定性 | 「分层降级：任何单点失败都不阻塞出片」——这是真的，工程上做得很扎实 |

#### ⚠️ 只能说一半

| 卖点 | 能说 | ❌ 不能说 |
|---|---|---|
| **一键去 AI 味** | 「128 条 AI 惯用词库 + 句长方差检测 + 反注入护栏 + 后台可运营词库」 | 「分句级重写」「去模板句」「随机化句式」——**32/33 条模式只检测不修复** |
| **音画自动对齐** | 「ASR 词级时间戳 + Levenshtein 窗口匹配，**数据层已落地**」 | 「成片字幕按真实语音对齐」——成片是字数估算；且中文以外未支持 |
| 批量改写 | 「知乎收藏夹批量改写，串行频控 + 失败回退原稿」 | 「通用批量改写 / 自动重试 / 逐条预览」 |
| 字幕生成 | 「分句块质量有共享向量回归测试保障」 | 「逐字时间戳精确」——是块内线性插值 |
| 素材自动补全 | 「缺素材时自动降级占位图，不阻塞出片」 | 「AI 智能补图」——无 provider 时是 ffmpeg 色块 |

#### ❌ 完全不能讲

**成本可见（S-46）· 多版本产出（S-06）· 多比例产出（S-34）· 标题/正文分位置（S-32）· 保留原作者口吻（S-30）· 内容复利素材库（S-25/S-26/S-56）· 视频克隆生产可用**

> 其中 **S-30 特别危险**：`imitate` 模式的 prompt 主动要求「相似度低于 40%」「不要使用原文中的标志性短语」（`rewrite-engine-core.js:458-459`）——这是**主动去原作者化**，跟卖点写的"保留原作者的味道"正好相反。这条如果说出去，是可验证的假话。

### 3.4 去 AI 味核心链路的三个技术债

| # | 债 | 修法 | 成本 |
|---|---|---|---|
| 1 | 33 条模式中 32 条只检测不修复 | 为高价值模式（`S1 级`）补 rewriter；或把 detect-only 模式明确降级为「评分项」并在 UI 标注 | 中。**先做后者（纯标注，半天），能立刻消掉"已处理"的错觉** |

| 3 | 零随机，同输入必同输出 | 引入受控随机（同义替换池轮转、句式变换变体）+ seed 可传入以保留可复现性 | 中。但**先有多版本产出才有意义**，见下 |

## 四、该做但还没做的需求（补齐类）

### 🔴 P0-1 · 操作审计日志（`R-AUDIT`）

**为什么第一**：这是矩阵团队和代运营的**合规入场券**。客户问「这条是谁发的」，现在答不上来，一次就可能丢单。

**现状**：只有「发布结果」，没有「谁在什么时候对哪个账号做了什么」。

**落地范围**：
1. `operation_log` 表（SQLite，与 `publish_history` 同生命周期）：`ts` / `operator_subject`（云端已有 Logto sub，本机用 owner_subject）/ `action` / `account_id` / `platform` / `target_ref`（taskId、contentId）/ `result` / `reason`
2. 埋点位置：发布发起、发布重试、账号增删、凭证重新登录、云端同步、批量操作
3. 界面：发布历史页每个任务卡片挂一个「详情」抽屉，展开看完整操作链
4. 导出：随 S-44 一起做（见 P1-3）

**工程注意**：
- `apps/desktop/src/views/Accounts.vue` 和 `Publish.vue` 体积已大，行数门禁 limit=500、增量容忍 200（`.github/scripts/check-max-lines.js:48-49`），**新增 UI 必须放新文件**，不要往大文件里塞。
- 审计表建议放 `packages/shared-utils/src/`，跟 `publish-audit-status.js` 同族，保证主进程/渲染层共用单一真源。

**为什么不是 in-flight change**：`publish-logging-observability` 做的是**系统日志**（故障排查用），这个要做的是**业务审计**（对外交付/自证用），两者字段和生命周期都不同，不要合并。

### 🔴 P0-2 · 真实支付闭环（`R-PAY`）

**为什么第二**：现在订阅读得懂、权益发得出、但**钱收不进来**。所有定价、卖点、投放素材最终都卡在这里。

**现状**：`identity_orders.channel` 支持 `'payment'`，但只有 `redeem` 和 `admin_grant` 有实现；桌面端是 `payment:simulate` 模拟通道。

**落地范围**：
1. 选定支付渠道（微信支付 / 支付宝，桌面端场景大概率是微信支付 + 扫码）
2. 下单 → 支付 → **回调验签** → `channel='payment'` 落库 → `status='paid'` → 触发 `subscription-service` 续期（复用现有的 `upsertSubscription + 订单 + 权益快照` 三连写事务，`postgres-commerce-store.js:86`）
3. 幂等：回调必须防重放（现有兑换码核销的行锁 + 条件更新双保险模式可直接复用，`postgres-commerce-store.js:60-73`）
4. 客户端：把 `payment:simulate` 换成真实下单 UI + 扫码 + 状态轮询

**工程注意**：这是**唯一一个必须动服务器端 + 客户端两端**的需求，排期上要预留联调窗口。现有 `subscription-service.js:152` 已经处理了"陈旧到期时间"和"订单重放"两个坑，改造时把支付回调接到同一条路径上，不要另起炉灶。

### 🔴 P0-2b · 定时发布常驻（`R-ALWAYS-ON`）　← v4 新增，我建议提到 P0

**为什么这是 P0**：A7 已经说明，**软件退出后定时任务全部停摆，且空闲状态关窗口 = 直接退出进程**。

**这不是一个体验问题，是商业模式问题**：

> 代运营按月付费，买的是"周一到周五自动铺、周末休息"。
> 而"周一到周五白天空闲"恰恰就是产品判定为"可以安全退出"的状态。
> **用户按订阅付了钱，一关窗口服务就停——这是退款理由，不是 bug 报告。**

**落地（三选一，按成本排序）**：

| 方案 | 做法 | 成本 | 效果 |
|---|---|---|---|
| **① 最小改动（推荐先做）** | 放宽 `window.js:155-166` 的关闭守卫：**只要存在未到点的定时任务就转托盘**，不要求有 running/queued 任务 | 极低，改几行 | 覆盖"用户主动关窗口"这个主要场景 |
| ② 托盘自启 | 开机自启 + 托盘常驻 + 退出确认时提示"还有 N 个定时任务未发出" | 中 | 覆盖"用户手动退出应用" |
| ③ 系统级计划任务 | Windows 计划任务 / systemd timer 拉起最小 headless 派发进程 | 高，跨平台成本大 | 最彻底，但投入产出比未必划算 |

**建议先做 ① + ②**：这两条加起来能覆盖绝大多数真实场景，成本远低于 ③。**做完之后 S-13 可以升回 S 级。**

**顺带要改的**：`publish.js:258` 批量排期入口目前**没有任何条数校验**（`batch-manager.js:192-209` `createBatch` 也只算 `total` 不校验 `length`），单批实际上无上限。加一个软上限（提示 + 二次确认）比硬拒绝体验好。

### 🟠 P1-3 · 权限与账号归属（`R-RBAC`）

**为什么第三**：这是**唯一能让代运营按"每个客户 N 元/月"收费**的能力。现在只能按人头卖个人版，客单价天花板很低。

**分三期做，别一次上全套**：

| 期 | 做什么 | 为什么这个顺序 |
|---|---|---|
| **第一期：账号分组** | 现在分组 CRUD + 面板 + 筛选**已经存在**（`openspec/changes/publish-permission-recheck` 提到），但只活在渲染层 `localStorage`，未落持久化真源、发布页也不消费。**把它落库 + 接进发布页**，成本极低，收益立竿见影 | 先有"客户"这个容器，才有"客户下的账号" |
| **第二期：操作人 + 归属** | `operator_subject` 记到每条账号上，发布时强制写进 `operation_log`；账号列表按归属人筛选 | 这一期就能支撑"哪个运营负责哪些号" |
| **第三期：角色权限** | 管理员 / 运营 / 只读 三个角色，对发布、凭证、导出三类操作分别授权 | 权限矩阵是第三期，因为前两期不做的话角色无处可挂 |

**红线**：**凭证查看/导出权限必须独立于发布权限**，且默认不给。这条处理不好会直接触发 S-62 描述的信任危机。

### 🟠 P1-4 · 稳定性可证明（`R-PROOF`）

**为什么需要**：痛点地图说「这六问答不上来，矩阵人群基本谈不成」。第 1 问答得出来（1/3/10 并发），但**"20 个号跑得动吗"需要压测数据支撑**，现在没有。

**落地**：
1. 定义并跑通三档压测基线：`1 号 × 7 平台 × 50 条` / `5 号 × 7 平台 × 50 条` / `10 号 × 7 平台 × 50 条`，记录成功率、P95 耗时、失败分布
2. 结果落成一张对外可发的容量表（和痛点地图 §7.2 的「省时测算表」同一个套路——**用真实数字把 B 级卖点升成 S 级**）
3. 应用内「服务状态」面板（`PRD-SERVICE-STATUS-PANEL` 已有）加一行当前并发/队列水位，让用户自己看

**成本很低，收益很高**，建议和第一批一起做。

### 🟠 P1-4b · 重试策略与失败告警（`R-RETRY` + `R-NOTIFY`）　← v4 新增

**这两条是"已经写好但没接线"，属于最便宜的一类修复。**

| 需求 | 现状 | 落地 |
|---|---|---|
| **R-NOTIFY 掉线/失败主动通知** | `publish-alert.js` 的 `triggerAlert`（`:79`）与 `sendNotification`（`:66`）**已实现但全仓零调用**；`login-status-monitor` 只在主窗口存在时发 IPC | ① 把 `triggerAlert` 接进发布失败与掉线事件；② 给 `login-status-monitor` 补一条 `new Notification`（建议带"30s 后重新检测"的按钮）。**做完 A8 就能恢复"第一时间知道"** |
| **R-RETRY 重试退避** | `task-queue.js:585` 裸 `push` 零退避；`retryable` 判据只有一个 `noRetry`，全仓仅 1 处设置 | ① 加指数退避 + 抖动；② 把 `adapters/_base/provider-error.js:29-42` 已有的 `retryable` 元数据表接进发布主链路；③ 认证失败 / 参数错误 / 审核拒绝三类设 `noRetry` |

> **为什么值得做**：矩阵团队的第一问就是"崩了谁负责"。**现在的答案是"会重试，但立刻重试，而且什么都重试"**——这听起来比不重试更不可靠。修完之后可以正面回答："失败自动重试 2 次，带指数退避；认证和参数错误不重试，直接告诉你原因。"
>
> **成本**：R-NOTIFY 是纯接线（小时级）；R-RETRY 需要补测试（`api-publish-engine` 测试 93/143 覆盖很好，风险低）。

### 🟡 P2-5 · 用量与成本可见（`R-COST`）

**为什么需要**：见 A6——S-46 现在是**零基础**，而它是痛点地图里给代运营的收尾杀手锏。同时它也支撑 S-28（自带 Key 的成本可控）这条 S 级卖点。

**落地**（三步，都不大）：
1. **记 token**：改写 / AI 写作 / story2video 三个主链路的 LLM 响应，把 `usage.prompt_tokens` / `completion_tokens` 透传到调用方。现在这些信息在适配器层被丢掉了。
2. **落库**：新增 `llm_usage` 表（时间 / 功能 / provider / 模型 / tokens_in / tokens_out），跟 `performance_snapshot` 同族，生命周期一致。
3. **展示**：客户端加一行「本月用量与折算金额」；金额按用户自己配的 provider 单价算（**不给官方积分算钱，避免和订阅制打架**——这同时化解了 A4 的风险敞口）。

**顺手收获**：有了这张表，S-46 之外还能支撑**配额预警**（快用完之前提醒），这是订阅制产品降低差评率的标准动作。

**注意**：这张表和 `ops-center` 的 `model_usage_daily` 语义不同——**那张是平台看调用量用的，这张是用户看自己花了多少用的**。不要合并，但上报时可以脱敏聚合后对齐，避免两套口径打架。

## 五、适合优化但不用新建模块的（优化类）

### O1 · 把「去 AI 味」的效果变成可交付的证据 ⭐ 最高性价比

**先说清楚现状**（第三节 3.2 有完整取证，这里只给结论）：

`ai-taste-remover.js` 的 3-pass 架构是真的，护栏设计（检测优先、反注入、人类基线保护、句长方差）也真的，但——

> **33 条结构/语气模式里 32 条只检测不修复**。三连排比、聊天残留、商业黑话、`不仅仅是…而是` 全部原样穿透。**检测器越完备，越容易给人"已经处理过了"的错觉。**

所以这一条的做法要改：**不能只做营销证据，必须同时把 detect-only 的部分暴露出来。** 否则就是在给一个半成品做放大。

**优化动作**（按顺序，前两步是纯标注/修 bug，不需要碰核心逻辑）：

| # | 动作 | 性质 | 成本 |
|---|---|---|---|
| 1 | **修 `_mergeUniformSentences` 标点问题**（`:875-896`）——现在会把反问句改成陈述句 | 修 bug，3 行改动 | 低，**建议立刻做** |
| 2 | UI 上把 detect-only 的模式明确标注为「评分项 · 未自动改写」 | 诚实 + 半天 | 极低 |
| 3 | 建**固定 20 条评测集**（10 条 AI 味重 + 10 条人工基准），每次改 prompt 跑一遍，输出改前/改后 + 四维质量分 | 回归基线 | 中 |
| 4 | 应用内做「改前/改后」并排对比视图 | 产品化 | 中 |
| 5 | 用评测结果出对比表，填进痛点地图 §7.2 的省时测算表 | 销售素材 | 低 |

> **第 1 步是 bug 不是 feature，但它的对外风险比任何话术都大**——用户看到自己的反问句被改成陈述句，第一反应是"这工具改坏我的东西了"。
>
> 第 3 步的评测集是**双用途**：既是销售素材，也是 CI 回归护栏。现在全仓 4 个 fixtures 目录没有一个用于改写质量，阈值调参没有客观锚点——这张表建起来，后面所有 prompt 改动才有安全网。

**做完之后 S-04 的实际口径**（不是"分句级去 AI 味"，那不成立）：
> 「128 条 AI 惯用词库 + 句长方差检测 + 反注入护栏 + 四维质量评估（改写充分度/语义保持度/相似度/原创性），词库后台可运营。」

**这条仍然是全表性价比最高的**——因为质量四维评估和 viralScorer 都已经真实注入了，缺的只是把 detect/repair 的真实比例诚实地摆出来。

### O2 · 把采集的反爬能力产品化

**现状**：`packages/collection-engine/src/default-strategies.json` 是一套相当专业的反爬策略层——每平台独立配置 `riskLevel` / `dailyBudget` / `interval` / `activeHours` / `weekendFactor` / `backoff`（指数退避）/ `circuitBreaker`（熔断 + 半开）/ `fetcher` 主备通道 / `needsLogin` / `warmup` / `behaviorIntensity`，再配合 `rate-limiter.js`、`circuit-breaker.js`、`cool-down-pool.js`、`health-monitor.js`、`behavior-simulator.js`、`audit-logger.js`。

**这是 S-40「账号风控友好」的真正证据，但现在藏在配置文件里，用户和话术都拿不到。**

**优化动作**：
1. 采集页加一个**「今日采集配额」可视化**（还有多少条、下一个平台什么时候能采、因为风控冷却了多久）
2. 把 `riskLevel` 翻译成用户能懂的话："知乎采集较频繁触发平台限制，我们已自动放慢节奏"
3. 这条同时解决痛点地图里「限流了怎么发现」的**采集侧**答案

采集平台覆盖：真实适配器 5 个（`platform-adapters/`：`bilibili` / `douyin` / `xiaohongshu` / `wechatmp` / `zhihu`），**S-01 待核实清单里问的「能不能采 B站/抖音/小红书」答案是都能**。

### O5 · 代运营「客户只读报告」 ⭐ 被忽略的付费点
