# 前端 UE 交互与用户体检研究方案

> 版本：v1.0 | 日期：2026-10-07 | 类型：Phase 0.1 技术调研 + Phase 4.1 质量体检
> 范围：`apps/desktop/src`（Electron 渲染层）+ `ops-center/frontend/src`（运营后台）
> 性质：**纯研究方案**，本次不产出任何代码改动；所有结论均附取证命令与文件行号，可复现。

---

## 0. 执行摘要

本轮体检覆盖 **562 个前端源文件 / 131,479 行**（desktop `src`）+ **42 个 view**（ops-center）。

**核心判断：项目的前端治理「机制」已经很健全，「内容」仍有明显欠账。**

项目已建成一套相当完整的前端机械门禁（`check-frontend-consistency` / `check-max-lines` / `check-color-literals` / `check-css-var-defined` / `check-route-registry` / `check-locale-sync`），以及 45 视图 + 32 工作流的视觉回归框架。`window.confirm` 与渲染层直连 IPC 已**清零**，`confirmDanger` 封装用了 51 处——这些是真做出来的东西。

但体检同时暴露三个结构性问题，它们不是"再加几个门禁"能解决的：

| # | 问题 | 量级 | 对用户的实际感受 |
|---|---|---|---|
| **P1** | **超大文件畸形化**，5 个文件 >2000 行，`CreateView.vue` 单文件 5588 行 | 98 个文件挂账超限 | 首屏慢、交互卡顿、任何改动都可能踩雷 |
| **P2** | **ops-center 后台 a11y 近乎空白**（42 view 仅 4 处 aria） | 4 / 42 | 键盘用户无法导航、读屏器静默 |
| **P3** | **i18n 只做了"门禁"没做完"迁移"**，`locale-cjk-baseline.json` 是一份数百条硬编码中文的欠条 | 数百条 | 切英文后 UI 半中半英 |

## 1. 体检方法论

### 1.1 为什么用「门禁基线」而不是「人工目测」

项目已有 6 个前端门禁脚本。本方案的全部数字**优先取自这些门禁的权威输出**，而非自造 grep——理由与项目既有实践一致：`scripts/classify-docs-only.js` 的注释明确写过「禁止人工目测、禁止第二份白名单」。同一事实若有两个来源，迟早对不上。

复现命令：

```powershell
node .github/scripts/check-frontend-consistency.js --json
node .github/scripts/check-max-lines.js
node .github/scripts/check-css-var-defined.js
node .github/scripts/check-color-literals.js
```

### 1.2 两个维度的定义

- **UE 用户交互维度**：用户「操作」产品时的路径是否清晰、反馈是否及时、可逆性是否足够。
- **用户体检维度**：产品的「身体指标」——性能、可访问性、一致性、健壮性——是否达标。

### 1.3 取证时的自我纠错记录

初稿曾用 `Select-String` 全仓 grep 得出「`window.confirm` 39 处」这一 alarming 数字。跑权威门禁后实际为 **0**——grep 把 `*.test.js` 里的断言字符串也算进去了。**这条纠错本身就是结论：自动化门禁的基线文件比人工统计更可信。**

## 2. UE 用户交互维度审查

### 2.1 信息架构：真源已建，元数据未填

项目已有正确架构决策——`apps/desktop/src/config/route-registry.js` 作为导航单一真源，侧边栏由 `deriveSidebarMenu(ROUTE_REGISTRY)` 派生，`check-route-registry.js` 会拦截「新增路由未登记」。

**但 `router/index.js` 的 38 条路由中，`meta` 字段只有 2 个 `title`**。这意味着：

- ❌ 无路由级标题 → 窗口标题 / 面包屑 / 历史记录全部拿不到语义
- ❌ 无 `requiresAuth` 之类的守卫声明 → 鉴权逻辑散落在各页面
- ❌ 无导航顺序声明 → IA 顺序只存在于侧边栏配置里，与路由表是两份认知

**优化建议**：把 `navEntry` 里的 `labelI18nKey` / `group` 反向同步为路由 `meta`，路由表升级为真正的 IA 声明源。当前是「注册表管菜单、router 管跳转」的分裂结构。

### 2.2 键盘可达性：「更多」菜单是断点

`MpSidebar.vue` 的整体质量在本次体检中属上乘——有 `aria-label="主导航"`、`aria-current`、`aria-expanded`、ResizeObserver 同步宽度、i18n 标签、fail-open 降级。**但「更多」折叠菜单存在明确缺陷：**

```vue
<!-- apps/desktop/src/layouts/MpSidebar.vue:53-68 -->
<div v-if="moreOpen && moreItems.length" class="mp-more-menu" role="menu">
  <router-link role="menuitem" ... >
```

- 声明了 `role="menu"` / `role="menuitem"`，**但没有任何方向键导航**（无 `@keydown` 处理 ArrowUp/ArrowDown/Home/End）
- `role="menu"` 按 WAI-ARIA 规范隐含「应用 roving tabindex」语义，当前是普通 tab 流，与 ARIA 期望行为不符
- 结果：键盘用户 Tab 进菜单能到达，但**无法用方向键在 44 个导航项间快速移动**——这是 `role="menu"` 带来的**实际可用性倒退**（用户预期方向键可用）

**两种解法**（择一）：
1. **补齐 roving tabindex + 方向键 + Esc 关闭 + 焦点回收**（保留 menu 语义，符合规范）
2. **去掉 `role="menu"`，改用普通导航列表语义**（务实，但放弃 ARIA menu 的效率优势）

推荐 **方案 1**，并顺手加 `@keydown.esc`。

### 2.3 反馈及时性：骨架屏缺失，长任务靠 toast 兜底

全项目 `el-skeleton` 用量 **0**，`v-loading` 仅 8 处，而 `ElMessage.*` 用了 212 处（success 62 / error 75 / warning 75）。

这个分布说明一件事：**团队把"反馈"默认理解成了 toast，而 toast 是最弱的反馈形态。**

- toast 会被新 toast 顶掉，长任务期间用户看不到进度
- `test:visual` 里有专门的 `StageProgress.vue`（阶段进度）说明长任务体验被认真对待过，但**这套模式没有推广到其他视图**
- 首屏加载（`Collection.vue` 2771 行、`Dashboard.vue` 796 行）无骨架屏 → 白屏/闪烁

**优化建议**：定义三层反馈规范并写进门禁——
1. **首屏/列表** → `el-skeleton`（不遮挡布局）
2. **局部操作** → `v-loading` + 按钮 loading 态 + **禁用重复提交**
3. **跨页面/长任务** → 进度条/阶段进度 + 可离开页面（后台继续）

### 2.4 操作可逆性：51 处确认弹窗，撤销几乎为零

`confirmDanger` 51 处、`el-dialog` 9 处、`el-drawer` 2 处——危险操作有拦截，这点做得对。

但 **`undo`/撤销 相关代码仅 5 处**。对一个内容生产工具（写文案、剪视频、配模型密钥）而言，这意味着**几乎所有破坏性操作都是单向门**：

- 删除采集内容 / 批量删除账号 / 修改模型密钥 → 一次确认，错则不可恢复
- 用户在 2771 行的 `Collection.vue` 里误删一条刚生成的内容，只能重新生成（消耗 Token/时间）

**优化建议**：分级可逆性——
- 低危（删除单条采集）→ **Toast 内 5 秒撤销**（软删除 + 撤销窗口）
- 中危（批量操作）→ `confirmDanger` + **操作清单预览**（"即将删除 12 条"）
- 高危（密钥覆盖、账号解绑）→ 保留 `confirmDanger`，但要求**输入确认**

### 2.5 多窗口/标签导航：复杂度已外溢到用户可感知

`onNavClick` 需要判定 `activeTabIsHomeShell` → 走 `navigateActiveHomeShell` IPC → 否则切 tab → 再 `router.push`。这个三段式回退（`MpSidebar.vue:176-196`）**本身是正确的防御**，但它存在的产品含义是：

> **用户点侧边栏时，不知道自己会跳到哪里。**

这不是代码缺陷，是**信息架构复杂度外溢**。38 条路由（含 `/board/:projectId`、`/replay/:projectId` 这类参数化深链）配上「更多」折叠，用户建立心智模型的成本很高。

**优化建议**：先做**行为度量**再谈改 IA——目前没有任何数据回答「用户最常去哪几个页面」「更多菜单展开率是多少」。**没有度量就重构 IA 是赌博。**

## 3. 用户体检维度审查

### 3.1 性能：渲染成本与响应式开销

| 指标 | 数值 | 判断 |
|---|---|---|
| `watch(` | 50 处 | 中 |
| `watchEffect` | 0 处 | 偏保守 |
| `deep: true` | 7 处 | 🟡 见下 |
| `v-for` | 287 处 | 需核查 key 覆盖 |
| `setTimeout` | 276 处 | 🟡 见下 |

**`deep: true` 的 7 处**集中在 `CreateView.vue:1787-1788`、`StageProgress.vue:279`、`ProductionBoard.vue:192`、`ConfigProfileManager.vue:451`、`GroupTagsEditor.vue:69`、`SceneAssetSelection.vue:268`。深度监听对**任意层级**属性变化都触发回调——在 5588 行的 `CreateView.vue` 上，这是明确的性能热点。

**`setTimeout` 276 处**需要分类，不能一律当罪。抽查 `CreateView.vue` 的四处：

```js
:1853  sceneAssetAttentionTimer  = setTimeout(... , 2000)          // UI 提示自动消失 — 合理
:2278  s2vOptionsToastTimer      = setTimeout(... , durationMs)    // toast 自动消失 — 合理
:2290  _lastOptionsSaveTimer     = setTimeout(... , 1000)          // 防抖保存 — 合理
```

这四处**都是正当的防抖/toast 定时器**，不是"硬编码等待"。项目规约里把 `setTimeout` 一律列为反模式过于粗糙——**建议门禁改为检测「等待远程状态」类反模式**（`setTimeout` 后紧跟 IPC 调用且无轮询/事件），而不是数个数。

### 3.2 可访问性：desktop 合格，ops-center 是空白

这是本轮**最清晰的、可立即行动**的缺口。

| 指标 | desktop | ops-center |
|---|---|---|
| view 数 | 46 | 42 |
| `aria-label` | 174 | **4** |
| `role=` | 150 | （含 aria 共 4） |
| `el-table` | — | 320 处 |
| `prefers-reduced-motion` | 22 | — |

**ops-center 是运营人员的生产工具**（配置应用菜单、管理模型密钥、看审计日志），却几乎没有任何 ARIA 标注。320 个 `el-table` 意味着大量**无障碍信息完全缺失**的数据表格。

根因很清楚：**门禁只覆盖 `apps/desktop/src`**。看 `check-frontend-consistency.js` 的常量：

```js
const SRC_ROOT = path.join(ROOT, 'apps', 'desktop', 'src')   // ← 硬编码根
const RENDERER_DIRS = ['views', 'components', 'composables', ...]
```

**ops-center 从未进入任何前端门禁视野。** 这是一个架构级的门禁盲区，不是疏漏。

**优化建议**：把 `check-frontend-consistency` / `check-css-var-defined` / `check-max-lines` 的扫描根改为「可配置的多根」，ops-center 纳入后立即建立新基线。

### 3.3 视觉一致性：设计 token 化的最后一段路

| 指标 | 当前 | 基线 | 趋势 |
|---|---|---|---|
| 品牌色字面量 `colorLiterals` | 129 | 129 | 持平 |
| 未定义 CSS 变量 `cssVarUndefined` | **59** | 64 | ✅ 下降 5 |

`--text-primary` / `--bg` / `--cohere-green` 等变量在 `AiWriterPanel.vue`、`BenchmarkChart.vue`、`ArticleEditor.vue` 中被引用但**从未定义**（无 fallback）。

后果直接命中用户：**主题切换时这些属性会失效**——因为 CSS 变量未定义，浏览器回退到继承/初始值，深色模式下可能出现文字与背景同色。**这是可见的、可截图证明的视觉 bug，不是理论风险。**

同时 `check-color-literals.js` 零增长但也没下降——说明门禁**只防新增、不促清偿**。129 处存量需要专门的收编批次。

### 3.4 健壮性与错误处理：错误分支数量健康

`ElMessage.error` 75 处 vs `ElMessage.success` 62 处，比例健康——**说明失败路径是被认真对待的**，这在本项目中是一个明显优势。

`v-html` 用量 **0**（XSS 面收敛良好），`console.log` 仅 15 处（生产日志污染低）。

`prefers-color-scheme: 0` —— 主题完全由用户设置驱动，无系统跟随。**这是产品决策，不是缺陷**，但需确认是否有意为之。

### 3.5 代码体量：98 个文件挂账超限

```
limit=500  growthAllowance=200  超限文件=98  挂账=98  墓碑=1
```

`check-max-lines.js` 状态为 PASS，但这**只意味着"没有新增超限文件"**——98 个存量挂账一个没动。TOP 榜：

| 文件 | 行数 |
|---|---|
| `views/CreateView.vue` | **5657** |
| `views/Collection.vue` | 2721 |
| `views/ResultView.vue` | 1882 |
| `views/Publish.vue` | 1730 |
| `views/ModelProviders.vue` | 1636 |

`CreateView.vue` 一个文件承载整个视频创作流程（模板 1–~4000 行 + 脚本到 5657 行），已挂账 6008 行的测试文件。**这是项目最大的单点风险**：任何对视频创作流程的改动都在触碰一个 5000+ 行的文件。

> 原则：**先度量、再改动**。每一波都必须有可验证的产出，不做无证据的批量重构。

## 5. 关键风险与不确定性

**诚实标注——以下是我没有验证的部分：**

1. **未做运行时验证**：本方案全部基于静态代码与门禁基线。「深色模式文字同色」是**基于 CSS 变量未定义的推断**，必须由 Wave 0.4 截图证实或证伪后才能作为结论。
2. **未做用户侧验证**：没有真人可用性测试。"IA 复杂"是代码结构推断，不是用户反馈。
3. **未测性能**：`CreateView.vue` 首屏时间、内存占用均未实测，"慢"是体量推断而非测量。
4. **`setTimeout` 276 处未逐个分类**：抽查 4 处均正当，但不能外推到全部。

**如果只能做一件事**：做 Wave 0.4（主题切换视觉巡检）。它是唯一能把"推断"变成"证据"的动作，成本最低而信息量最大——可能直接挖出影响全部用户的可见 bug。
