> 版本：v1.1（CCG 双家族评审修订版）| 日期：2026-10-07 | 类型：Phase 0.1 技术调研 + Phase 4.1 质量体检
> 范围：`apps/desktop/src`（Electron 渲染层）+ `ops-center/frontend/src`（运营后台）
> 性质：**本次交付物仅为本文档**。第 4 章 Wave 0-5 是**后续执行阶段的规划**，不属本次交付范围；Wave 中涉及运行时代码的部分需另开 worktree 走完整门禁。

### 数字口径约定（v1.1 修订）

全文数字只有两种来源，正文每个指标均标注是哪一种：

- **【门禁】** —— 来自既有门禁脚本的 JSON/文本输出，权威、可复现。复现命令见第 6 章。
- **【抽样】** —— 来自本次 `Select-String` 统计，**抽样推断**，可能与门禁口径不同（含测试文件与否、实例数与文件数之别）。已在各处注明计数范围。

> 口径不统一是 v1.0 的主要缺陷：同一个文件曾出现 5588 / 5655 / 5657 三个行数。v1.1 统一以门禁为权威。

## 0. 执行摘要

本轮体检覆盖 **562 个前端源文件 / 131,479 行**【抽样】（desktop `src`）+ **desktop 46 个 view / ops-center 39 个顶层 view + 1 个 settings 子页**。

**核心判断：项目的前端治理「机制」已经很健全，「内容」仍有明显欠账。**

项目已建成一套相当完整的前端机械门禁（`check-frontend-consistency` / `check-max-lines` / `check-color-literals` / `check-css-var-defined` / `check-route-registry` / `check-locale-sync`），以及 45 视图 + 32 工作流的视觉回归框架。`window.confirm` 与渲染层直连 IPC 已**清零**【门禁】，这些是真做出来的东西。

但体检同时暴露三个结构性问题。**下表右列是推断，不是已验证结论**——第 5 章明确列出哪些尚未验证，各问题的验证动作见 Wave 0。

## 1. 体检方法论

### 1.1 为什么用「门禁基线」而不是「人工目测」

项目已有 6 个前端门禁脚本。**凡门禁能给出的数字一律以门禁为准**（标【门禁】），门禁覆盖不到的指标才用 `Select-String` 抽样统计（标【抽样】）——理由与项目既有实践一致：`scripts/classify-docs-only.js` 的注释明确写过「禁止人工目测、禁止第二份白名单」。

**门禁覆盖不到的领域（必须用【抽样】）**：a11y 标注数量、反馈形态分布（toast/skeleton/dialog）、`setTimeout` 数量、导航项数量。这些门禁没有对应脚本，因此其数值**只代表抽样结果，不保证与任何权威口径一致**，引用时须连同计数范围一起看。

复现命令：

```powershell
# 【门禁】口径
node .github/scripts/check-frontend-consistency.js --json
node .github/scripts/check-max-lines.js
node .github/scripts/check-css-var-defined.js
node .github/scripts/check-color-literals.js

# 【抽样】口径（仅用于门禁未覆盖的指标）
Get-ChildItem apps/desktop/src -Recurse -Filter *.vue | Select-String -Pattern 'aria-label' | Measure-Object
```

### 1.2 两个维度的定义

- **UE 用户交互维度**：用户「操作」产品时的路径是否清晰、反馈是否及时、可逆性是否足够。
- **用户体检维度**：产品的「身体指标」——性能、可访问性、一致性、健壮性——是否达标。

### 1.3 取证时的自我纠错记录

初稿曾用 `Select-String` 全仓 grep 得出「`window.confirm` 39 处」这一 alarming 数字。跑权威门禁后实际为 **0**【门禁】——grep 把 `*.test.js` 里的断言字符串也算进去了。

**这次纠错划清了口径边界**：门禁有对应脚本的指标用【门禁】，没有的用【抽样】并注明范围。v1.0 曾把两者混用且未标注，是本文档自身的缺陷。

## 2. UE 用户交互维度审查

### 2.1 信息架构：真源已建，元数据未填

项目已有正确架构决策——`apps/desktop/src/config/route-registry.js` 作为导航单一真源，侧边栏由 `deriveSidebarMenu(ROUTE_REGISTRY)` 派生，`check-route-registry.js` 会拦截「新增路由未登记」。

**但 `router/index.js` 的 38 条路由中，`meta` 字段只有 2 个 `title`**【抽样：统计 `path:` 与 `meta` 字段出现次数】。这意味着：

- ❌ 无路由级标题 → 窗口标题 / 面包屑 / 历史记录拿不到语义
- ⚠️ **已核实**：`grep -rn "beforeEach|beforeResolve" apps/desktop/src`（排除测试文件）**无任何结果**——即项目**确实没有全局导航守卫**，鉴权与状态判断分散在各页面内部。这是实证结论，非推断。
- ❌ 无导航顺序声明 → IA 顺序只存在于侧边栏配置里，与路由表是两份认知

> 注：v1.0 曾据「meta 无 requiresAuth」推断「鉴权散落」，属过度推断——全局守卫本可不依赖 meta。v1.1 已改为先查证再下结论。

**优化建议**：把 `navEntry` 里的 `labelI18nKey` / `group` 反向同步为路由 `meta`，路由表升级为真正的 IA 声明源。当前是「注册表管菜单、router 管跳转」的分裂结构。

### 2.2 键盘可达性：「更多」菜单是断点

`MpSidebar.vue` 的整体质量在本次体检中属上乘——有 `aria-label="主导航"`、`aria-current`、`aria-expanded`、ResizeObserver 同步宽度、i18n 标签、fail-open 降级。**但「更多」折叠菜单存在明确缺陷：**

```vue
<!-- apps/desktop/src/layouts/MpSidebar.vue:53-68 -->
<div v-if="moreOpen && moreItems.length" class="mp-more-menu" role="menu">
  <router-link role="menuitem" ... >
```

- 声明了 `role="menu"` / `role="menuitem"`，**但没有任何方向键导航**（无 `@keydown` 处理 ArrowUp/ArrowDown/Home/End）
- `role="menu"` 按 WAI-ARIA 规范隐含「应用 roving tabindex」语义，当前是普通 tab 流，与 ARIA 期望行为不符
- 结果：键盘用户 Tab 能进入「更多」菜单，但**无法用方向键在其子项间快速移动**——这是 `role="menu"` 带来的**实际可用性倒退**（用户见到 menu 语义即预期方向键可用）

> 口径更正：v1.0 曾写「44 个导航项」，该数字实为 `route-registry.js` 中 `navEntry` 标记的出现次数（`grep -c navEntry`），**不等于导航项数**。实际导航项数量由运营中心下发配置决定，静态无法确定——这本身说明 IA 规模对客户端不可见。

**两种解法**（择一）：
1. **补齐 roving tabindex + 方向键 + Esc 关闭 + 焦点回收**（保留 menu 语义，符合规范）
2. **去掉 `role="menu"`，改用普通导航列表语义**（务实，但放弃 ARIA menu 的效率优势）

推荐 **方案 1**，并顺手加 `@keydown.esc`。

### 2.3 反馈及时性：骨架屏缺失，长任务靠 toast 兜底

以下均为【抽样】（`Select-String` 统计 `apps/desktop/src/**/*.vue`，含测试外的全部 .vue）：`el-skeleton` 用量 **0**、`v-loading` **8** 处、`ElMessage.success` **62** / `.error` **75** / `.warning` **75**（合计 212）。

这个分布提示一件事：**团队把"反馈"默认实现成了 toast，而 toast 是最弱的反馈形态。**（这是对分布的解读，非实测用户行为）

- toast 会被新 toast 顶掉，长任务期间用户看不到进度
- `test:visual` 里有专门的 `StageProgress.vue`（阶段进度）说明长任务体验被认真对待过，但**这套模式没有推广到其他视图**
- 首屏加载（`Collection.vue` 2721 行【门禁】、`Dashboard.vue` 796 行【门禁】）无骨架屏 → 推断为白屏/闪烁，**未实测**

**优化建议**：定义三层反馈规范并写进门禁——
1. **首屏/列表** → `el-skeleton`（不遮挡布局）
2. **局部操作** → `v-loading` + 按钮 loading 态 + **禁用重复提交**
3. **跨页面/长任务** → 进度条/阶段进度 + 可离开页面（后台继续）

### 2.4 操作可逆性：51 处确认弹窗，撤销几乎为零

`confirmDanger` 51 处、`el-dialog` 9 处、`el-drawer` 2 处——危险操作有拦截，这点做得对。

但 **`undo`/撤销 相关代码仅 5 处**。对一个内容生产工具（写文案、剪视频、配模型密钥）而言，这意味着**几乎所有破坏性操作都是单向门**：

- 删除采集内容 / 批量删除账号 / 修改模型密钥 → 一次确认，错则不可恢复
- 用户在 2721 行的 `Collection.vue` 里误删一条刚生成的内容，只能重新生成（消耗 Token/时间）

**优化建议**：分级可逆性——
- 低危（删除单条采集）→ **Toast 内 5 秒撤销**（软删除 + 撤销窗口）
- 中危（批量操作）→ `confirmDanger` + **操作清单预览**（"即将删除 12 条"）
- 高危（密钥覆盖、账号解绑）→ 保留 `confirmDanger`，但要求**输入确认**

### 2.5 多窗口/标签导航：复杂度已外溢到用户可感知

`onNavClick` 需要判定 `activeTabIsHomeShell` → 走 `navigateActiveHomeShell` IPC → 否则切 tab → 再 `router.push`。这个三段式回退（`MpSidebar.vue:176-196`）**本身是正确的防御**，但它存在的产品含义是：

> **用户点侧边栏时，不知道自己会跳到哪里。**

这不是代码缺陷，是**信息架构复杂度外溢**。38 条路由（含 `/board/:projectId`、`/replay/:projectId` 这类参数化深链）配上「更多」折叠，用户建立心智模型的成本很高。

**优化建议**：先做**行为度量**再谈改 IA——目前没有任何数据回答「用户最常去哪几个页面」「更多菜单展开率是多少」。**没有度量就重构 IA 是赌博。**

## 3. 用户体检维度审查

### 3.1 性能：渲染成本与响应式开销

| 指标 | 数值 | 判断 |
|---|---|---|
| `watch(` | 50 处 | 中 |
| `watchEffect` | 0 处 | 偏保守 |
| `deep: true` | 7 处 | 🟡 见下 |
| `v-for` | 287 处 | 需核查 key 覆盖 |
| `setTimeout` | 276 处 | 🟡 见下 |

**`deep: true` 的 7 处**【抽样】集中在 `CreateView.vue:1787-1788`、`StageProgress.vue:279`、`ProductionBoard.vue:192`、`ConfigProfileManager.vue:451`、`GroupTagsEditor.vue:69`、`SceneAssetSelection.vue:268`。深度监听对**任意层级**属性变化都触发回调——在 5657 行的 `CreateView.vue` 上，这**可能**是性能热点。**未做性能实测**，需在 Wave 0 用 devtools 火焰图确认。

**`setTimeout` 276 处**【抽样】需要分类，不能一律当罪。抽查 `CreateView.vue` 的四处：

```js
:1853  sceneAssetAttentionTimer  = setTimeout(... , 2000)          // UI 提示自动消失 — 合理
:2278  s2vOptionsToastTimer      = setTimeout(... , durationMs)    // toast 自动消失 — 合理
:2290  _lastOptionsSaveTimer     = setTimeout(... , 1000)          // 防抖保存 — 合理
```

这四处**都是正当的防抖/toast 定时器**，不是"硬编码等待"。项目规约里把 `setTimeout` 一律列为反模式过于粗糙——**建议门禁改为检测「等待远程状态」类反模式**（`setTimeout` 后紧跟 IPC 调用且无轮询/事件），而不是数个数。

### 3.2 可访问性：desktop 合格，ops-center 是空白

这是本轮**最清晰的、可立即行动**的缺口。

本表全部为【抽样】（`Select-String` 统计各目录 `.vue`）：

| 指标 | desktop | ops-center | 口径说明 |
|---|---|---|---|
| view 文件数 | 46（顶层 34 + 子目录 12） | 40（顶层 39 + settings 1） | `views/**/*.vue` 文件计数 |
| `aria-label` | 174 | **4** | 出现次数（同一标签多次渲染只计 1 次） |
| `role=` | 150 | （含 aria 共 4） | 同上 |
| `el-table` | — | 32 个**文件** / 320 处**实例** | v1.0 误写「320 个表格」，实为实例数 |
| `prefers-reduced-motion` | 22 | — | 出现次数 |

**ops-center 是运营人员的生产工具**（配置应用菜单、管理模型密钥、看审计日志），却几乎没有任何 ARIA 标注——42 个 view 中仅 4 处 aria，对比 desktop 的 174 处。32 个含数据表格的 view 意味着大量**无障碍信息缺失**的数据表格。

> 口径更正：v1.0 写「ops-center 42 view / 320 个 el-table」，两个数字口径都不准（view 数应为 40，`el-table` 是实例数不是文件数）。

根因很清楚：**门禁只覆盖 `apps/desktop/src`**。看 `check-frontend-consistency.js` 的常量：

```js
const SRC_ROOT = path.join(ROOT, 'apps', 'desktop', 'src')   // ← 硬编码根
const RENDERER_DIRS = ['views', 'components', 'composables', ...]
```

**ops-center 从未进入任何前端门禁视野。** 这是一个架构级的门禁盲区，不是疏漏。

**优化建议**：把 `check-frontend-consistency` / `check-css-var-defined` / `check-max-lines` 的扫描根改为「可配置的多根」，ops-center 纳入后立即建立新基线。

### 3.3 视觉一致性：设计 token 化的最后一段路

| 指标 | 当前 | 基线 | 趋势 |
|---|---|---|---|
| 品牌色字面量 `colorLiterals` | 129【门禁】 | 129 | 持平 |
| 未定义 CSS 变量 `cssVarUndefined` | **59**【门禁】 | 64 | ✅ 下降 5 |

`--text-primary` / `--bg` / `--cohere-green` 等变量在 `AiWriterPanel.vue`、`BenchmarkChart.vue`、`ArticleEditor.vue` 中被引用但**从未定义**（无 fallback）——这是 `check-css-var-defined.js` 的直接输出，事实层面确定。

**但由此推出的用户影响此前是推断——Wave 0.4 已完成实测，结论如下（2026-10-07 验证）：**

| 结论 | 证据 |
|---|---|
| ✅ **未定义变量确实导致深色模式可读性缺陷** | 18 个视图全部存在低对比文本，合计 61 个样本（阈值 3:1） |
| ⚠️ **缺陷有两个方向，不是一个** | ①深字压深底（accounts 整页 1.13:1、home「快捷入口」1.14:1）②浅字压浅底（dashboard 试用横幅 1.09:1） |
| 🔴 **现有巡检工具检测不到这类问题** | `dark-mode-audit.js` 报「0 可疑」，因其启发式只统计**接近纯白(≥240)的背景像素**；文字色失效时背景仍是深色，落在检测盲区 |
| ❌ **原 v1.0/v1.1 表述需修正** | 曾写「可能是文字与背景同色」——方向对，但机制描述不完整（未预见浅压浅这一形态） |

**最严重的三个定点案例**（已用 `contrast-probe.js` 打印祖先链确认未触发白色兜底，非误报）：

| 元素 | 文字色 | 实际背景 | 对比度 |
|---|---|---|---|
| `accounts/.accounts-page` 整页文字 | `rgb(40,40,47)` 深 | `rgb(30,30,35)` 深 | **1.13:1** |
| `home/h3.mp-home-section-title`「快捷入口」 | `rgb(37,37,43)` 深 | `rgb(26,26,30)` 深 | **1.14:1** |
| `dashboard/.trial-banner .banner-text` | `rgb(232,232,237)` 浅 | `rgb(243,240,255)` 浅 | **1.09:1** |

> 截图证据：`apps/desktop/tests/visual-testing/reports/dark-audit/dashboard-dark.png` —— 三个统计卡片的「0」与标签在深色模式下肉眼几乎不可读。

**新增产出（填补既有工具盲区）**：
- `tests/visual-testing/scripts/contrast-audit.js` —— 遍历可见文本元素，取 computed `color`/`backgroundColor` 算 WCAG 对比度，输出低于阈值者
- `tests/visual-testing/scripts/contrast-probe.js` —— 定点探针，打印祖先链背景，用于**证伪**误报（检测是否触发白色兜底）

**对 Wave 0.4 验收标准的修正**：原定「59 处未定义变量的实际渲染截图 / 证明或排除深色模式可读性 bug」→ 已完成，且结论是**证实**（且比预期更严重：现有巡检工具本身有盲区）。

同时 `check-color-literals.js` 零增长但也没下降——说明门禁**只防新增、不促清偿**。129 处存量需要专门的收编批次。

### 3.4 健壮性与错误处理：错误分支数量健康

`ElMessage.error` 75 处 vs `ElMessage.success` 62 处【抽样】——两者比例接近，**提示**失败路径被认真对待。（这是对代码分布的解读，非用户实测反馈）

`v-html` 用量 **0**【抽样】（XSS 面收敛良好），`console.log` 仅 15 处【抽样】。

`prefers-color-scheme: 0`【抽样】—— 主题完全由用户设置驱动，无系统跟随。**这是产品决策，不是缺陷**，但需确认是否有意为之。

### 3.5 代码体量：98 个文件挂账超限


### 8.2 三轮巡检与结果

| 轮次 | 工具 | 结果 |
|---|---|---|
| 第 1 轮 | `dark-mode-audit.js`（既有） | 18 视图，「白色残留 >15%」可疑 **0 个** |

### 8.3 关键发现：既有工具的盲区

`dark-mode-audit.js` 的判据是「统计接近纯白（≥240）的**背景**像素占比」。这个启发式只能发现**深色模式出现大面积浅色块**。

但 59 处未定义变量里含 `--text-primary`（**文字色**）。文字色失效时元素背景**仍是深色** —— 于是「深字压深底」和「浅字压浅底」两种形态**都落在检测盲区里**。这就是它报 0 可疑、而实际 18 视图全有问题的原因。

**教训**：巡检工具自身的判据也要被质疑。「工具全绿」不等于「问题不存在」，尤其当该工具的判据只覆盖问题的一个子集时。

### 8.4 本轮未覆盖（不假装已闭合）
