### S-21　数据在你自己电脑上

**原文**
> 你的素材库、账号信息、草稿都存在你自己电脑上。
> 「你的内容只在你自己的电脑上。」

**判定**：🔴 **说错就是信任事故。** 我在 v4 曾把"凭证信封加密上云"当作正面证据，**那是服务端侧的加密，客户端上行是明文**。代码注释原文（`cloud-accounts/handlers.js:220`）：

```js
// 上行是明文凭证（PRD §7.2 / ADR-0003：加密发生在服务端，桌面端没有也不该有 KMS 访问权）。
```

即：**客户端 → 服务端 = 明文（TLS 内）→ 服务端 KMS = 加密存储 → 下行 = 服务端解密后明文**。这是为了实现"换设备免扫码"的显式设计，不是 bug，但**对外说法必须如实**。

**同时界面文案本身就不准确**——用户看到的是「登录凭证将**加密后**上传」，实际是「上传后**由服务端**加密」。

**改写后**
> **一句话**：账号和素材默认存在你自己的电脑上。开启云同步后，登录凭证会通过加密通道上传、由服务器加密保存——这是为了让你换电脑时不用重新扫码。你可以随时一键断开并清除云端数据。
> **强度** A ｜ **来源** ✅ 本地真源 + 显式授权 + 可断开（已确认）

**🚫 绝对不能说**：「凭证不出本机」「内容不过第三方」「端到端加密」

**⚠️ 另需在隐私说明里如实列出四条上报**（用量 / 发布结果 / 失败诊断 / 配置下发），**目前这三条 reporter 未发现用户可见开关**，而 ops-center 地址已内置在 `identity-public.json:22`。**这条需人工复核设置页**。

### S-62　凭证加密存储（这条是站得住的，建议加强）

**原文**
> 各平台登录凭证加密保存，不是明文躺在硬盘上。
> 「我们不拿你的账号做文章。」

**判定**：✅ **✅ 经深审确认成立，而且比卖点写的更强。**

`crypto.js:80-100` 在 safeStorage 不可用时 encrypt/decrypt **直接 throw**，注释明写「refusing plaintext fallback」。`credential-store.js`、`ops-center-sync.js`、Python 侧 `douyin_auth.py` / `bilibili.py` / `xiaohongshu_auth.py` **全部一致 fail-closed**，全仓无明文降级路径。

**加强建议**：把「**拒绝明文降级**」直接写进投放素材——竞品基本没人敢这么写，是能打的差异点。

### S-21 配套：⚠️ Windows 构建完全未签名

**这一条不能靠改话术解决，建议单独决策。**

```json
"win": { "sign": false, "signAndEditExecutable": false, "signDlls": false }
"publish": { "provider": "github", "owner": "Colinchiu007", "repo": "mulpub" }
```

更新走 `electron-updater` 的 GitHub provider（下载源恒为 GitHub Releases，无 `setFeedURL`），**但产物不做代码签名**，发布者是个人 GitHub 账号。

> **为什么对这个产品特别重**：我们卖的核心信任是"你的 15 个平台账号凭证都在你本机、加密存着"。这条信任的唯一物理基础是**本机主密钥 + 不可篡改的更新通道**。更新包一旦被顶替，**所有本地加密的承诺同时失效**——不需要破解任何加密，让用户装一个别的 exe 就够了。
>
> **对内建议**：话术改成只讲事实、不做绝对承诺（「数据在你本机、密钥经系统级加密」）；**对 ToB / 代运营客户，这条会被技术尽调直接问**，建议提前备答案。
> **中期**：上代码签名证书（OV/EV）。

### S-39　多账号身份隔离，不串号

**原文**
> 每个账号独立环境，A 号的草稿不会出现在 B 号的草稿箱。
> 「串号这种事我们不允许发生。」

**判定**：🔴 **当前最危险的一条。** 登录态与草稿隔离是真的，但**发布并发维度没有按账号隔离**——在途 change `publish-throughput-optimization` 自陈：全局并发 3 不看「平台+账号」维度，**同账号两条任务可同时各开一个隐藏浏览器窗口操作同一创作者后台**，且进度路由是 last-write-wins。正在修，但未合并。

**改写后（修复合并前）**
> **一句话**：每个账号独立的登录环境，A 号的草稿不会出现在 B 号的草稿箱。
> **对比**：串号是矩阵运营最恶心的 bug——客户 A 的内容发到客户 B 的号上，一次就流失一个客户。
> **怎么说**：「A 号的草稿，不会出现在 B 号的草稿箱。」
> **强度** A（**从 S 降级**）｜ **来源** 🔶 登录态隔离 ✅ / 发布并发隔离 ⏳ 在途

> ⏳ **解锁强话术的条件**：`publish-throughput-optimization` 合并 + 补一轮「同账号串行」回归测试通过。届时可升回 S 级并恢复「串号这种事我们不允许发生」。

### S-13　定时发布：加一句前提

**原文**
> 攒好的内容批量排期，到点自动发。
> 「周末备货，工作日自动发。」

**判定**：🔴 **卖点场景和产品行为正好相反。** 定时发布是纯主进程内存定时器（`scheduler.js:271`），应用退出即停（`shutdown.js:50-52`）；而且**空闲状态下关窗口 = 直接退出进程**（`window.js:155-166` 只在「托盘可用 + 有 running/queued 任务」时拦截关闭）。代运营的核心用法恰恰是"白天空闲、周末休息"——**这正是产品判定为"可以安全关掉"的状态**。

**改写后**
> **一句话**：软件开着（含最小化到托盘）时会按时发；关掉软件不会发，下次启动会把过期的补上。
> **怎么说**：「排期要在软件开着的时候才准。别关，让它缩到托盘就行。」
> **强度** A（**从 S 级降级**）｜ **来源** ✅ 行为已确认，⚠️ 缺口：无系统级调度

> ⏳ **解锁条件**：放宽关闭守卫（存在未到点定时任务就转托盘）+ 托盘自启。**做完可升回 S 级。**
> 📌 另：批量排期入口目前**无条数校验**（`batch-manager.js:192-209` 只算 `total` 不校验 `length`），单批实际上无上限——建议加软上限提示。
