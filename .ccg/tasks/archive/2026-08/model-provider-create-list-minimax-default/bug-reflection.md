# Bug Reflection — 新增模型可见性与 MiniMax Image 配置

## 现象与复现

- **现象**：在“添加服务商”向导选择远程预设后，即使不填 API Key 也会显示保存成功；回到默认“已配置”列表时，新增项因没有可用凭据被过滤，用户误以为没有保存。
- **现象**：MiniMax Image 同时暴露 `image-01` 与 `image-01-live`，表单要求填写模型列表，调用方还能覆盖请求模型；这与固定使用 `image-01` 的产品约定冲突。
- **复现**：打开模型设置 → 添加服务商 → 选择图片生成 → MiniMax Image → 不填写 API Key 保存；或为 MiniMax Image 传入 `model: 'image-01-live'` 后检查请求体。
- **预期**：远程服务商缺少有效 API Key 时前端阻止保存、主进程也拒绝写入；成功创建的远程服务商刷新后出现在“已配置”列表。MiniMax Image 的预设、历史列表、表单和请求始终只使用 `image-01`。

## 5 Whys

1. 为什么保存后新增项不在列表？默认视图只显示有可用凭据的服务商。
2. 为什么无凭据记录仍显示保存成功？预设已经带入 ID、名称、Base URL 与模型列表，前端仅检查“名称或 ID”，随后 `create -> already exists -> update` 成功返回。
3. 为什么主进程没有拦截？`createProvider()` 允许远程服务商使用空 Key 写入禁用记录。
4. 为什么测试未发现？CRUD 测试只覆盖保存成功后的刷新及错误响应，没有覆盖“预设完整但 Key 为空”的负路径；测试夹具还隐含允许空 Key 创建远程服务商。
5. **根因**：服务商的“表单字段存在”“凭据可调用”“列表可见”三种状态没有形成同一份显式合同，空 Key 记录跨层获得了矛盾的成功语义。

MiniMax 漂移链：种子预设、适配器静态模型列表和 `generateImage(params.model)` 各自维护模型集合，缺少固定模型的单一规范化入口。

## 漏测分类与逃逸链

- **PRD 缺口**：PRD 只描述“可添加多个服务商”，没有明确远程服务商保存前必须有 API Key、固定模型不得被调用参数覆盖。
- **代码缺陷**：前端验证过弱；主进程创建入口未防御直调 IPC；MiniMax 三层配置不一致；本地免 Key 适配器初次按 Key 判断会造成可见性错误。
- **测试缺口**：缺少空 Key 创建拒绝、创建成功后列表回读、存量 MiniMax 双模型规范化、请求覆盖模型被忽略，以及本地免 Key 的 `is_configured` 状态回归。
- **流程缺口**：此前评审没有沿“新增向导 → IPC → DB → 列表筛选”检查成功反馈是否与可见性一致；没有按 Provider 对固定模型配置做跨层契约核对。

## 修复与回归保护

1. `ModelProviderManager.createProvider()` 对远程服务商要求非空 API Key；仅 Piper、Local Diffusion、ComfyUI 且回环地址可免 Key。该规则在主进程执行，IPC 直调不能绕过。
2. `useModelProviderCrud` 在提交前给出同一验证提示，避免用户看到伪成功；成功创建后的真实刷新测试断言新增项存在。
3. `normalizeProviderModels()` 统一 MiniMax Image 的预设、存量列表与更新写入为 `['image-01']`；适配器固定请求 `image-01` 并只暴露一个模型。
4. 主进程返回 `is_configured`，且要求记录已启用并有可用 Key（或合法本地免 Key）；渲染层使用该状态，避免禁用本地预设被伪装为已配置。

## 测试建议与执行

- **单元 / 状态覆盖**：空 Key 阻止保存、主进程拒绝远程空 Key、本地免 Key 已启用才显示已配置、成功刷新后新增项可见。
- **适配器契约**：MiniMax Image 的静态模型列表和请求体均固定为 `image-01`，并覆盖调用方传入旧模型时不被采纳。
- **桌面冒烟**：真实 Electron 进入设置页，确认预设和分类可见；选择 MiniMax Image 时不出现模型 ID 输入。
