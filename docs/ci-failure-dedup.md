# ci-failure 单的两种形态与处置口径

> 建立于 2026-10-05（issue #2635 处置决策：选项 2「封存」）。
> 这份文档的存在理由：`CI Failure Handler` 曾经一口气在仓库里堆了 742 张 open 单，
> 任何「现在还有哪些 CI 问题」的判断都会被这批噪声淹没。本文给出**形态区分 + 处置口径**，
> 让「历史档案」与「当前信号」在列表层面就能分开。

---

## 1. 两种形态，按标题一眼可辨

| | 旧形态（per-commit） | 新形态（签名） |
|---|---|---|
| 标题 | `ci-failure-<40 位 commit sha>: <Workflow> 失败` | `ci-failure[<类别>] <Workflow>: <job> / <step>[ :: <测试文件>]` |
| 去重键 | **提交** | **成因**（工作流 + job + 步骤 + 测试文件） |
| 同一因复发时 | 永远开新单（旧单命中不了） | 在**同一张单上追加评论** |
| 标签 | 额外打 `legacy-per-commit` | 只有 `ci-failure` 等 |
| 语义 | 某一次 push 上发生过一次失败 | 这条成因**当前是否还在复现** |
| 处置 | **封存**，保持 OPEN | 静默且门禁已绿 ⇒ 结单；近期有评论 ⇒ 保持 OPEN |

**为什么不能把旧形态「折叠」掉**：旧单键在 commit sha 上，同一成因在 `Electron CI` 名下有上百张彼此等价的单。让新签名去「匹配」它们只能任选一张挂复发记录 —— 那是把随机选择伪装成同因归并，比开着更坏。唯一的诚实收敛是按成因折叠，而折叠 = 批量 close/comment，属共享状态变更，必须逐条凭证据、经确认再做。

本次决策（2026-10-05，用户拍板）是**封存**而非折叠：成本低、完全可逆、不伪造归并关系。

---

## 2. 封存口径（742 张旧形态）

- 统一标签 `legacy-per-commit`（灰色，描述里写明「不代表当前状态」）
- **不 close、不评论、不改正文**
- 判定脚本：标题匹配 `/^ci-failure-[0-9a-f]{40}:/`

批量打标走 GraphQL 别名批量（`addLabelsToLabelable` 只接受**单个** `labelableId`），两个必须记住的坑：

1. `gh api graphql` 的 `-f/-F` **只能传标量**。把 `[ID!]!` 变量喂 JSON 数组会被当成单个 ID 字符串，报
   `Could not resolve to a node with the global id of '["LA_..."]'` ⇒ **id 一律内联字面量**。
2. 别名一多，GitHub 会返 **HTTP 504**，且返回的是 HTML 错误页而不是 JSON ⇒ 必须**重试 + 退避**，批次压到 10。

---

## 3. 新形态的结单判据（两条都成立才关）

1. **该门禁当前是绿的。** 2026-10-05 实测：main push 自 2026-10-02 起的 100 条 Actions 运行中，
   除 `CI Failure Handler (Level 4)` 的 skipped 外**全部 success，零 failure、零 cancelled**。
2. **同因未复发。** 签名去重按标题检索 ⇒ 复发表现为**在同一张单上追加评论**。
   所以「最后一条评论距今超过 3 天」是比「单子开着」强得多的存活判据。

两条不矛盾时要留意：main 的 push 运行整体绿，**但某个具体签名仍可能在 PR 事件上复现** ——
旧形态单开出时的失败多发生在 PR 侧。所以判据 1 用 main push 全局证据，判据 2 用本单自己的评论时间轴。

### 本轮分诊结果（2026-10-05）

| 处置 | 张数 | 说明 |
|---|---|---|
| 结单（comment + close） | 32 | 零评论或最后评论 ≤ 2026-10-02 |
| 保持 OPEN + 分诊评论 | 9 | 最后评论 ≥ 2026-10-03，**仍在复发**，逐条列了信号与判据 |

保持 OPEN 的 9 张里，`QG Changes / Detect docs-only changes`（15 条评论）与
`Doc Sync Gate`（25 条评论）是复发最密集的两条，值得优先看。

---

## 4. 读这份文档时的纪律

- **「仓库里有 742 张 ci-failure 单」不代表有 742 个问题。** 那是历史档案的体量。
- 判断当前健康度看两处：Actions 面板的最近运行结论，以及**新形态单里最近 3 天有评论的那些**。
- 本仓的既有范式可复用：`scripts/check-gate-record-debt.js` + `gate-record-debt-ledger.json`
  讲的是「批量归因 + 登记欠账 + 逐条销账」，与本文的「封存 ≠ 结单」是同一套纪律的两种应用。
